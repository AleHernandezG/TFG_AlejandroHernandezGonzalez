2. Módulo Autenticación y Registro
CU-01 — Registro con correo y contraseña
IdentificadorCU-01
NombreRegistro con correo y contraseña
Versión1.0
AutorAlejandro Hernández González
Actor principalACT-01 — Usuario Anónimo
DescripciónPermite a un visitante crear una cuenta nueva introduciendo nombre, email y contraseña. El sistema valida los datos, persiste el usuario y dispara el flujo de verificación por email antes de permitir el acceso.
PrecondiciónEl usuario no tiene cuenta en Cookr o no tiene sesión activa.
PostcondiciónCuenta creada en MongoDB con contraseña hasheada (bcrypt). Email de verificación enviado via Gmail SMTP. Usuario redirigido a pantalla de verificación pendiente.
PrioridadAlta — funcionalidad de entrada al sistema
FrecuenciaUna vez por usuario
FLUJO PRINCIPAL
1 Usuario Anónimo El usuario accede a /registro.
Sistema Muestra el formulario de registro (nombre, email, contraseña, confirmación).
2 Usuario Anónimo El usuario rellena todos los campos y pulsa Crear cuenta.
Sistema Valida el formulario con Zod (formato email, longitud contraseña ≥ 8 caracteres, coincidencia).
3 Sistema Comprueba que el email no esté ya registrado en MongoDB.
4 Sistema Genera hash bcrypt de la contraseña y persiste el documento de usuario con cuentaVerificada: false.
5 Sistema Genera un token de verificación (cadena hexadecimal de 64 caracteres) con TTL de 24 h y lo guarda en la colección tokens con type: 'verificacion'.
6 Sistema Envía el email de verificación con el enlace firmado via Gmail SMTP (Nodemailer).
7 Sistema Redirige al usuario a la pantalla «Verifica tu correo».
FLUJOS ALTERNATIVOS
FA-01 Sistema El email ya existe en la base de datos. → Devuelve error «Este correo ya está registrado». El formulario permanece visible con el campo email marcado.
FA-02 Sistema La contraseña no cumple los requisitos de Zod. → Muestra mensaje de validación inline sin enviar la petición al servidor.
FLUJOS DE EXCEPCIÓN
FE-01 Sistema Fallo en el envío del email. → La cuenta queda creada pero se muestra aviso «No pudimos enviarte el correo» con opción de reenvío manual.
CU-02 — Verificación de cuenta por email
IdentificadorCU-02
NombreVerificación de cuenta por email
Versión1.0
AutorAlejandro Hernández González
Actor principalACT-01 — Usuario Anónimo (con token de verificación)
DescripciónConfirma la titularidad del email mediante un enlace de un solo uso. Sin este paso el usuario no puede acceder a las funcionalidades autenticadas.
PrecondiciónEl usuario ha completado CU-01 y ha recibido el email con el enlace de verificación. La cuenta tiene cuentaVerificada: false.
PostcondiciónEl campo cuentaVerificada pasa a true en MongoDB. El token de verificación queda invalidado. El usuario puede iniciar sesión.
PrioridadAlta
FrecuenciaUna vez por cuenta
FLUJO PRINCIPAL
1 Usuario Anónimo El usuario abre el enlace del email (/verificar-email?token=<hex64>).
Sistema Extrae el token de la URL y busca el documento correspondiente en la colección tokens con type: 'verificacion'.
2 Sistema Comprueba que el token existe y no ha expirado (TTL 24 h).
3 Sistema Actualiza el usuario: cuentaVerificada: true. Elimina el token de la colección.
4 Sistema Muestra pantalla de confirmación «¡Cuenta verificada!» con botón hacia /login.
FLUJOS ALTERNATIVOS
FA-01 Sistema El token no existe o ya fue usado. → Muestra error «Enlace de verificación inválido» con opción de solicitar uno nuevo.
FA-02 Sistema El token ha expirado (más de 24 h). → Muestra error «Enlace caducado» y ofrece reenviar el email de verificación.
CU-03 — Inicio de sesión con correo y contraseña
IdentificadorCU-03
NombreInicio de sesión con correo y contraseña
Versión1.0
AutorAlejandro Hernández González
Actor principalACT-01 — Usuario Anónimo
DescripciónAutentica al usuario mediante email y contraseña usando NextAuth CredentialsProvider. El backend valida las credenciales comparando el hash bcrypt almacenado.
PrecondiciónEl usuario tiene cuenta en Cookr con cuentaVerificada: true.
PostcondiciónSesión NextAuth activa (JWT almacenado en cookie HttpOnly). Usuario redirigido al home (/home). Si el perfil está incompleto, redirige a /completar-perfil.
PrioridadAlta
FrecuenciaAlta — cada inicio de sesión
FLUJO PRINCIPAL
1 Usuario Anónimo El usuario accede a /login.
Sistema Muestra el formulario con campos email y contraseña.
2 Usuario Anónimo El usuario introduce sus credenciales y pulsa Iniciar sesión.
Sistema NextAuth CredentialsProvider envía las credenciales al endpoint /api/auth/callback/credentials.
3 Sistema El backend busca el usuario por email en MongoDB y compara la contraseña con bcrypt.compare().
4 Sistema NextAuth genera el JWT de sesión y lo almacena en una cookie HttpOnly; Secure; SameSite=Lax.
5 Sistema El callback session inyecta id, username y perfilCompleto en el objeto de sesión.
6 Sistema Si perfilCompleto: true → redirect a /home. Si false → redirect a /completar-perfil.
FLUJOS ALTERNATIVOS
FA-01 Sistema La contraseña no coincide con el hash. → NextAuth lanza error de autorización. Se muestra «Credenciales incorrectas» sin especificar qué campo falla.
FA-02 Sistema La cuenta existe pero cuentaVerificada: false. → Se muestra «Debes verificar tu correo antes de iniciar sesión» con opción de reenvío.
FA-03 Sistema El usuario no existe en MongoDB. → Error genérico igual que FA-01 para evitar enumeración de usuarios.
CU-04 — Inicio de sesión con Google OAuth
IdentificadorCU-04
NombreInicio de sesión con Google OAuth
Versión1.0
AutorAlejandro Hernández González
Actor principalACT-01 — Usuario Anónimo
DescripciónPermite autenticarse usando la cuenta de Google mediante el flujo OAuth 2.0 gestionado por NextAuth GoogleProvider. Elimina la necesidad de contraseña y verificación manual de email.
PrecondiciónEl usuario tiene cuenta Google activa. La aplicación tiene las credenciales OAuth configuradas en Google Cloud Console.
PostcondiciónSesión NextAuth activa. Si es el primer acceso, se crea el usuario en MongoDB y se redirige a completar perfil. Si ya existe, se redirige al feed.
PrioridadAlta
FrecuenciaAlta
FLUJO PRINCIPAL
1 Usuario Anónimo El usuario pulsa Continuar con Google en /login o /registro.
Sistema NextAuth redirige al endpoint de autorización de Google con response_type=code.
2 Usuario Anónimo El usuario selecciona su cuenta Google y autoriza el acceso.
Sistema Google devuelve un código de autorización al callback /api/auth/callback/google.
3 Sistema NextAuth intercambia el código por los tokens de acceso y obtiene el perfil del usuario (email, nombre, avatar).
4 Sistema El callback signIn verifica si el email ya existe en MongoDB. Si no existe, crea el documento de usuario con cuentaVerificada: true y perfilCompleto: false.
5 Sistema Si es nuevo usuario → redirect a /completar-perfil. Si ya existe → redirect a /home.
FLUJOS ALTERNATIVOS
FA-01 Usuario Anónimo El usuario cancela el popup OAuth de Google. → NextAuth redirige de vuelta a /login sin crear sesión ni mostrar error.
FA-02 Sistema El email de Google ya está registrado con contraseña. → NextAuth vincula ambos métodos de acceso al mismo documento de usuario existente.

PrecondiciónEl usuario tiene cuenta registrada con email y contraseña (no OAuth exclusivo). Tiene acceso al buzón de correo asociado a la cuenta.

Sistema Busca el email en MongoDB. Si existe, genera un token hexadecimal de 64 caracteres con TTL de 1 h y lo guarda en la colección tokens con type: 'reset'.
3 Sistema Envía el email con el enlace /reset-password?token=<hex64> via Gmail SMTP. Muestra mensaje genérico de confirmación independientemente de si el email existe.

FA-03 Sistema La nueva contraseña no supera la validación Zod. → Muestra errores inline sin consumir el token.
CU-06 — Completar perfil tras registro
IdentificadorCU-06
NombreCompletar perfil tras registro
Versión1.0
AutorAlejandro Hernández González
Actor principalACT-02 — Usuario Registrado (recién creado)
DescripciónOnboarding obligatorio que recoge los datos de perfil necesarios para la experiencia personalizada. El middleware de Next.js redirige automáticamente a esta pantalla si el perfil está incompleto.
PrecondiciónEl usuario tiene sesión activa y perfilCompleto: false en su documento de MongoDB (primer acceso tras registro o primer OAuth).
PostcondiciónPerfil completo: username único, avatar, preferencias dietéticas y alérgenos guardados. perfilCompleto: true. Usuario redirigido al home.
PrioridadAlta
FrecuenciaUna vez por usuario
FLUJO PRINCIPAL
1 Sistema El middleware detecta perfilCompleto: false en el token de sesión. Redirige a /completar-perfil y bloquea el acceso al resto de rutas protegidas.
2 Usuario Registrado El usuario introduce un nombre de usuario (username).
Sistema Valida disponibilidad en tiempo real mediante debounce con GET /api/auth/check-username. Muestra indicador de disponibilidad.
3 Usuario Registrado El usuario selecciona su dieta (omnívoro, vegetariano, vegano…) y sus alérgenos.
Sistema Registra las selecciones en el estado local del formulario.
4 Usuario Registrado El usuario sube o recorta una foto de avatar (opcional).
Sistema Procesa la imagen con el recortador integrado.
5 Usuario Registrado El usuario pulsa Empezar.
Sistema Envía POST /api/auth/completar-perfil con todos los datos. Actualiza perfilCompleto: true en MongoDB.
6 Sistema Actualiza el token JWT de NextAuth con el nuevo estado. Redirige a /home.
FLUJOS ALTERNATIVOS
FA-01 Sistema El username elegido ya está en uso. → Muestra «Este nombre de usuario no está disponible». El botón de envío permanece deshabilitado.
FA-02 Sistema El usuario no sube foto de avatar. → El sistema asigna un avatar generado con las iniciales del nombre sobre fondo de color derivado del username.
FA-03 Sistema El usuario intenta navegar a otra ruta. → El middleware intercepta la navegación y redirige de vuelta a /completar-perfil.

DescripciónIntegración con la Edamam Nutrition Analysis API que calcula automáticamente los valores nutricionales de una receta a partir de sus ingredientes con cantidades. Se ejecuta de forma asíncrona tras la publicación de la receta para no bloquear la respuesta al usuario. Planificado para Fase 6 del proyecto.
PrecondiciónLa receta ha sido publicada con lista de ingredientes que incluyen nombre, cantidad y unidad. Las variables EDAMAM_APP_ID y EDAMAM_APP_KEY están configuradas en el entorno del backend.
PostcondiciónEl documento de receta en MongoDB queda enriquecido con el campo nutricion que incluye calorías totales, proteínas, hidratos de carbono y grasas por porción. Los datos se muestran en el detalle de la receta.
PrioridadMedia — funcionalidad de valor añadido
FrecuenciaUna vez por receta al publicar o actualizar ingredientes
FLUJO PRINCIPAL
1 Sistema La receta es publicada correctamente (CU-13) y devuelta al cliente. El backend encola una tarea asíncrona para calcular la información nutricional sin bloquear la respuesta.
2 Sistema Construye el payload para Edamam: lista de ingredientes con formato «cantidad unidad nombre» (p. ej. «200g harina de trigo»). Envía POST https://api.edamam.com/api/nutrition-details con las credenciales app_id y app_key.
3 Sistema Edamam procesa la solicitud y devuelve el análisis nutricional completo. Extrae los valores relevantes: calorías (kcal), proteínas (g), hidratos de carbono (g), grasas (g) y fibra (g) por porción (total dividido entre el número de raciones).
4 Sistema Actualiza el documento de receta en MongoDB con el campo nutricion. El componente de detalle de receta muestra la tabla nutricional al usuario.
FLUJOS ALTERNATIVOS
FA-01 Sistema Edamam no reconoce alguno de los ingredientes → Devuelve el análisis parcial con los ingredientes que sí reconoció. El sistema guarda los datos disponibles e indica en la receta que el cálculo es aproximado.
FA-02 Sistema La cuota de la API de Edamam se agota → Las nuevas recetas publicadas se encolan para su análisis nutricional cuando la cuota se renueve. Las recetas sin datos nutricionales se muestran con un aviso «Información nutricional no disponible».
FLUJOS DE EXCEPCIÓN
FE-01 Sistema La API de Edamam no está configurada o devuelve error → El campo nutricion permanece nulo. El detalle de la receta no muestra la sección nutricional. No se interrumpe la publicación de la receta.
CU-39 — Envío de email transaccional (Gmail SMTP)
IdentificadorCU-39
NombreEnvío de email transaccional (Gmail SMTP)
Versión1.0

Actor principalACT-04 — Sistema (Gmail SMTP via Nodemailer)
Actores secundariosACT-01 / ACT-02 — Usuario destinatario del email
DescripciónServicio transversal de envío de emails del sistema. Utiliza Nodemailer con el proveedor Gmail SMTP autenticado mediante App Password. Se encarga del envío de todos los emails generados por la plataforma: verificación de cuenta, recuperación de contraseña y futuras notificaciones. Cada tipo de email usa una plantilla HTML independiente.
PrecondiciónSe ha producido un evento del sistema que requiere notificación por email: registro de cuenta (CU-01), solicitud de recuperación de contraseña (CU-05) o cualquier evento transaccional configurado. Las variables GMAIL_USER y GMAIL_APP_PASSWORD están presentes en el entorno del backend.
PostcondiciónEl email con el contenido correspondiente al evento ha sido enviado al buzón del usuario destinatario. El evento queda registrado en los logs del servidor.
PrioridadAlta — bloquea los flujos de registro y recuperación
FrecuenciaBaja — solo en eventos de cuenta específicos
FLUJO PRINCIPAL
1 Sistema Un evento del sistema dispara la necesidad de enviar un email (p. ej. registro nuevo → verificación de cuenta). El servicio de email selecciona la plantilla HTML correspondiente al tipo de evento.
2 Sistema Construye el objeto de email: destinatario (to), asunto (subject), cuerpo HTML con los datos dinámicos del evento (nombre del usuario, enlace con token firmado, fecha de expiración).
3 Sistema Nodemailer establece la conexión SMTP con smtp.gmail.com:465 usando las credenciales GMAIL_USER y GMAIL_APP_PASSWORD.
4 Sistema Envía el mensaje. Gmail SMTP devuelve confirmación de entrega con el messageId. El sistema registra el evento en los logs del servidor.
5 Actor El usuario recibe el email en su buzón y actúa sobre él (hace clic en el enlace de verificación o de reset).
Sistema El flujo continúa en el caso de uso que originó el envío (CU-02 para verificación, CU-05 para reset de contraseña).
FLUJOS DE EXCEPCIÓN
FE-01 Sistema El servidor SMTP rechaza la conexión o las credenciales → Nodemailer lanza excepción. El backend registra el error en los logs y, si el evento lo permite (p. ej. registro), continúa el flujo principal indicando al usuario que el email no pudo enviarse, con opción de reenvío manual.
FE-02 Sistema La dirección de destino no existe o el buzón está lleno → Gmail devuelve un error de entrega (bounce). El sistema registra el fallo. En futuros envíos al mismo email puede mostrar un aviso al usuario para que compruebe su dirección.
