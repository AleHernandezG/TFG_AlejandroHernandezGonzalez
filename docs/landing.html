1. ¿Qué es la landing page y para qué sirve?

La landing page es la primera pantalla que ve cualquier persona que entra a Gastronómica. Su único objetivo es convencer al visitante de que se registre o inicie sesión. No requiere estar logueado para verla y no hace ninguna consulta al servidor — todo el contenido está escrito directamente en el código (datos "mock" o de prueba).

Visualmente se divide en cuatro bloques que el usuario ve de arriba a abajo al hacer scroll:

Orden visualBloque¿Qué hace?
1º (pantalla completa) SeccionHero Carrusel de fondo animado + titular + dos botones (Crear cuenta / Ya tengo cuenta)
2º (al hacer scroll) BentoTestimonios 6 tarjetas con opiniones de usuarios de la app
3º (al seguir bajando) BentoCaracteristicas 3 tarjetas explicando las funciones principales de la app
4º (al final de la página) PiePagina Footer con stack tecnológico, enlaces y aviso de IA
¿Por qué no hay navegación (navbar) en la landing? Es una decisión de diseño deliberada. Se quiere que el visitante se centre únicamente en el mensaje y los botones de registro/login, sin distracciones. El header de navegación aparecerá una vez el usuario esté dentro de la app.

2. Conceptos clave para entender el código

Si eres nuevo en React o Next.js, estos son los conceptos que aparecen constantemente en este código y que necesitas entender antes de leer los componentes:

¿Qué es un componente?

Un componente es simplemente una función de JavaScript que devuelve HTML (técnicamente JSX). Cada bloque visual de la página es un componente. Se pueden reutilizar, anidar unos dentro de otros y pasarles datos como parámetros (llamados props). 

// Ejemplo simplificado de componente
function MiComponente({ titulo }) {
  return <h1>{titulo}</h1>;
}

// Uso: <MiComponente titulo="Hola mundo" />

"use client" — Componente de cliente vs servidor

En Next.js 14 hay dos tipos de componentes. Por defecto, los componentes son de servidor (se renderizan en el servidor y el navegador recibe HTML estático). Si el componente necesita interactividad (useState, useEffect, eventos de ratón...) hay que marcarlo con "use client" al principio del archivo para que se ejecute también en el navegador. Todos los componentes de la landing usan "use client" porque tienen animaciones.

useState — Guardar información que cambia

useState es la forma de guardar un valor que puede cambiar y que, cuando cambia, hace que el componente se vuelva a dibujar en pantalla. Por ejemplo, el número del slide activo del carrusel se guarda con useState: cuando cambia de 0 a 1, React redibuja el fondo del hero.

useEffect — Ejecutar código "al lado"

useEffect permite ejecutar código después de que el componente se dibuje en pantalla. Se usa para cosas como temporizadores, llamadas a APIs o suscripciones a eventos. En el carrusel del hero, useEffect arranca el intervalo de 5 segundos que avanza los slides.

Framer Motion — Las animaciones

Framer Motion es una librería que permite animar componentes de React de forma declarativa. En vez de escribir CSS de animación complejo, defines el estado inicial (hidden) y el estado final (show) y Framer Motion hace la transición automáticamente. El concepto de variantes permite que un componente padre coordine las animaciones de todos sus hijos a la vez (stagger = aparecen uno tras otro con un retardo).

Barrel export (index.ts)

En vez de importar cada componente desde su ruta completa, existe un archivo index.ts que reexporta todo. Así, en lugar de escribir tres imports largos, se escribe uno solo: 

// Sin barrel export (molesto):
import { SeccionHero }        from "@/features/landing/components/seccionHero";
import { BentoCaracteristicas } from "@/features/landing/components/bentoCaracteristicas";
import { BentoTestimonios }    from "@/features/landing/components/bentoTestimonios";

// Con barrel export (limpio):
import { SeccionHero, BentoCaracteristicas, BentoTestimonios } from "@/features/landing/components";

3. Estructura de archivos

El proyecto sigue una arquitectura feature-based: en lugar de agrupar los archivos por tipo (todos los componentes juntos, todos los estilos juntos…), se agrupan por funcionalidad. Todo lo relacionado con la landing vive dentro de features/landing/, lo que facilita encontrar y modificar cosas.

(9 más) │ └── features/ └── landing/ ← Todo lo propio de la landing page ├── components/ │ ├── seccionHero.tsx ← Pantalla inicial con carrusel │ ├── bentoCaracteristicas.tsx ← Grid de 3 funcionalidades │ ├── bentoTestimonios.tsx ← Grid de 6 testimonios │ ├── tarjetaTestimonio.tsx ← Carta individual de un testimonio │ └── index.ts ← Barrel export └── data/ └── datosLanding.ts ← Todos los textos y datos mock
Regla importante sobre la carpeta ui/ Los archivos dentro de components/ui/ son generados automáticamente por shadcn/ui y no se deben modificar manualmente. Si necesitas personalizar un componente de shadcn, se hace desde fuera (pasando props o con clases de Tailwind), nunca editando los archivos de ui/.

4. Cómo se conectan los componentes

La landing page funciona como un árbol: page.tsx es la raíz y el resto de componentes cuelgan de él. Cuando Next.js recibe una petición a la ruta /, ejecuta page.tsx, que a su vez renderiza cada componente hijo en orden.

app/page.tsx ← ruta "/" ← punto de entrada de la landing │ │ Define el contenedor de animación (motion.div) │ Importa y monta los 4 componentes principales │ ├── renderiza SeccionHero │ features/landing/components/seccionHero.tsx │ Autónomo — gestiona su propio estado (slideActivo) │ No recibe props del padre │ ├── renderiza motion.div ← contenedor de Framer Motion │ │ Coordina las animaciones de sus hijos (stagger) │ │ Se activa al entrar en el viewport (whileInView) │ │ │ ├── renderiza BentoTestimonios │ │ features/landing/components/bentoTestimonios.tsx │ │ Lee testimoniosLanding desde datosLanding.ts │ │ Renderiza una TarjetaTestimonio por cada testimonio │ │ │ │ │ └── renderiza ×6 TarjetaTestimonio │ │ features/landing/components/tarjetaTestimonio.tsx │ │ Recibe un objeto Testimonio como prop │ │ Recibe variants para participar en el stagger │ │ │ └── renderiza BentoCaracteristicas │ features/landing/components/bentoCaracteristicas.tsx │ Lee caracteristicasLanding desde datosLanding.ts │ Renderiza una Card por cada característica │ └── renderiza PiePagina components/common/piePagina.tsx Sus datos (stackTecnologico, enlacesUtiles) están hardcodeados en el propio archivo

¿Cómo se pasan datos entre componentes?

En React, los datos fluyen siempre de padre a hijo mediante props. En esta landing hay dos patrones de paso de datos:

Patrón Quién lo usa Cómo funciona

5. Cada componente explicado en detalle

5.1 — page.tsx  app/page.tsx

¿Qué es? Es el punto de entrada de la ruta /. En Next.js 14 (App Router), cualquier archivo llamado page.tsx dentro de app/ se convierte automáticamente en una página. Este archivo no contiene casi lógica: su única responsabilidad es montar los componentes en el orden correcto y configurar el contenedor de animaciones que coordina a los hijos.

¿Por qué tiene "use client"? Porque usa motion.div de Framer Motion, que necesita JavaScript en el navegador para funcionar. Sin ese directive, Next.js lo renderizaría solo en el servidor y las animaciones no funcionarían.

Variables que define:

  • contenedor — objeto de variantes de Framer Motion que define la animación del bloque central (fade in + stagger de 0.1s entre hijos). Actúa como director de orquesta.
  • PaginaInicio — función del componente (export default). Next.js la llama al servir la ruta /.

Estructura JSX que renderiza:

<main>
  <SeccionHero />

  <motion.div variants={contenedor} whileInView="show">  ← activa al hacer scroll
    <BentoTestimonios />
    <BentoCaracteristicas />
  </motion.div>

  <PiePagina />
</main>
¿Por qué BentoTestimonios va antes que BentoCaracteristicas? Orden visual de la página: primero los testimonios (prueba social — convencer al visitante) y después las características (explicar qué hace la app). Es una decisión de UX/copywriting, no técnica.

5.2 — SeccionHero  features/landing/components/seccionHero.tsx

¿Qué es? La primera pantalla que ve el usuario. Ocupa el 100% del alto de la ventana (min-h-screen). Contiene un carrusel de fondos animado, un titular, un subtítulo y dos botones de acción.

Estado interno (useState):

  • slideActivo — número del slide que se está mostrando ahora mismo (0, 1, 2 ó 3). Empieza en 0.

Efectos (useEffect + useCallback):

  • siguienteSlide — función que incrementa slideActivo en 1, volviendo a 0 al llegar al final. Está envuelta en useCallback para que no se recree en cada render.
  • El useEffect arranca un setInterval de 5000ms que llama a siguienteSlide automáticamente. Cuando el componente se desmonta, el clearInterval del return limpia el temporizador para evitar fugas de memoria.

Cómo funciona el carrusel:

El fondo no es un carrusel HTML tradicional. Es una serie de motion.div donde solo se renderiza el slide activo (identificado por key={slideActivo}). AnimatePresence de Framer Motion detecta cuándo un elemento desaparece del DOM y anima su salida antes de eliminar el anterior y animar la entrada del nuevo. El modo "popLayout" evita que los slides se superpongan con z-index incorrecto durante la transición.

Capas de overlay sobre el fondo:

Para que el texto blanco sea legible sobre cualquier gradiente de color, se apilan 3 capas semitransparentes sobre el fondo:

CapaEfectoPor qué
25% oscuro uniformeOscurece todo el fondoBase de legibilidad
Gradiente vertical (abajo más oscuro)La zona del texto queda más oscuraEl texto está centrado y abajo
Gradiente horizontal (laterales oscuros)Enfoca la atención al centroEfecto cinematográfico

Datos que consume:

  • slidesHero de datosLanding.ts — array de 4 slides, cada uno con gradiente, emoji y etiqueta

Los dos CTAs (call to action):

5.3 — BentoTestimonios  features/landing/components/bentoTestimonios.tsx

¿Qué es? Una sección con un encabezado y un grid de 6 tarjetas de testimonios. El nombre "bento" hace referencia al estilo de cuadrícula japonesa (bento box) donde elementos de distintos tamaños se distribuyen en un grid.

¿Qué hace exactamente? Este componente no contiene el HTML de cada tarjeta: su única responsabilidad es iterar el array de testimonios y renderizar un TarjetaTestimonio por cada uno, pasándole los datos correspondientes. Es el patrón contenedor/presentador: BentoTestimonios es el contenedor y TarjetaTestimonio es el presentador.

Grid responsive:

PantallaColumnasAncho aproximado
Móvil1 columna< 640px
Tablet2 columnas640px – 1023px

¿Cómo se pasan las animaciones a los hijos?

BentoTestimonios define dos objetos de variantes (contenedor y elemento) y pasa elemento como prop variants a cada TarjetaTestimonio. Framer Motion automáticamente conecta las variantes del hijo con las del padre: cuando el contenedor pasa a estado "show", activa las animaciones de todos los hijos en cascada (stagger).

6. Los datos: datosLanding.ts

features/landing/data/datosLanding.ts es el único lugar donde viven todos los textos y contenidos de la landing. Si mañana hay que cambiar un testimonio, el título de una característica o añadir un slide al carrusel, solo hay que tocar este archivo. Ningún componente define textos propios — los reciben de aquí.

Excepción: PiePagina y los textos dentro del JSX del hero (el titular principal, el subtítulo) sí están escritos directamente en sus componentes, porque son textos únicos que no tiene sentido externalizar.

Los tipos son "contratos" que definen qué forma tiene cada objeto de datos. TypeScript comprueba en tiempo de compilación que los datos cumplen el contrato, evitando errores como pasar un número donde se espera un string.

7. Las animaciones: cómo funciona Framer Motion aquí

Framer Motion funciona mediante el concepto de variantes: se define cómo debe verse un elemento cuando está "escondido" (hidden) y cómo cuando está "visible" (show), y la librería genera la transición automáticamente.

Sistema de variantes compartidas (stagger)

El truco del efecto "los elementos aparecen uno tras otro" (stagger) funciona así: el componente padre define staggerChildren: 0.1 en su variante show, lo que significa "activa a mis hijos con 0.1s de retraso entre cada uno". Los hijos solo necesitan definir su animación propia (fade + subir desde abajo) — Framer Motion gestiona el timing automáticamente. 

// Padre — coordina el timing
const contenedor = {
  hidden: { opacity: 0 },
  show: { opacity: 1, transition: { staggerChildren: 0.1 } }
}

// Hijo — solo define su propia animación
const elemento = {
  hidden: { opacity: 0, y: 20 },        // invisible, 20px más abajo
  show:   { opacity: 1, y: 0 }          // visible, posición normal
}

// TarjetaTestimonio recibe "elemento" como prop variants
// y participa en el stagger del padre automáticamente

Trigger: whileInView

Las animaciones del bloque central no se ejecutan al cargar la página sino al hacer scroll. whileInView="show" activa la variante show cuando el elemento entra en el viewport del navegador. viewport={{ once: true }} significa que la animación solo ocurre una vez (no se repite al volver a subir).

Carrusel del Hero: AnimatePresence

El hero usa un mecanismo diferente. AnimatePresence es especial: detecta cuando un componente hijo va a desaparecer del DOM y le permite ejecutar una animación de salida antes de eliminarse. Sin AnimatePresence, el slide anterior desaparecería instantáneamente. Con él, el slide viejo hace fade out mientras el nuevo hace fade in + scale desde 1.06 hasta 1.

8. El sistema de diseño

Variables de color (OKLch)

En lugar de usar colores hexadecimales o RGB directamente, se usan variables CSS definidas en globals.css. Esto permite cambiar toda la paleta desde un solo lugar, y tener un tema claro y uno oscuro (aún pendiente de implementar). El formato OKLch es más moderno que HSL/RGB: percibe mejor la diferencia de brillo entre colores (útil para accesibilidad).

Variable CSSUsoColor aproximado
--backgroundFondo de la páginaCasi blanco cálido
--foregroundTexto principalCasi negro suave
--brandColor principal de la appNaranja-marrón cálido
--cardFondo de las tarjetasBlanco puro
--muted-foregroundTexto secundario / subtítulosGris medio
--borderBordes de componentesGris muy claro
--brand-subtleFondos con toque de brand (avatares)Naranja muy pálido

En el código de Tailwind se usan como bg-background, text-foreground, text-brand, border-border/40 (con opacidad), etc.

Tipografía

VariableFuenteUso
--font-sansGeist (variable font)Texto general, títulos
--font-monoGeist Mono (variable font)Código, datos técnicos

Ambas fuentes se cargan localmente con next/font/local desde la carpeta app/fonts/, evitando peticiones externas a Google Fonts (mejor rendimiento y privacidad).

Breakpoints responsive (mobile-first)

"Mobile-first" significa que el CSS base está escrito para móvil y los breakpoints añaden estilos para pantallas más grandes. En Tailwind, los prefijos activan reglas a partir de ese ancho:
