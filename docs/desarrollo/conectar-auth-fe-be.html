Sprint 2 · Auth FE → BE

Conexión Auth FE → BE real

Documentación de todos los cambios realizados para conectar el frontend de autenticación con los endpoints reales del backend Express. Build ✅ · Lint ✅ · 0 errores.

1. Contexto y punto de partida

El backend de auth ya estaba operativo desde el Sprint 2 BE (Express en puerto 4000, 5 endpoints). El frontend tenía los 4 formularios de auth con mocks de setTimeout simulando latencia. La carpeta frontend/src/services/ existía pero vacía.

El objetivo era crear la capa de servicios y conectar cada formulario al backend sin tocar la UI (solo las funciones alEnviar).

📐 Arquitectura obligatoria: Componente → Hook → Service → apiClient → Backend. Ningún componente importa Axios directamente ni conoce URLs de la API.

2. Archivos nuevos

NUEVO frontend/src/services/apiClient.ts

Instancia Axios centralizada. Toda la comunicación HTTP del FE pasa por aquí.

import axios from "axios";

export const apiClient = axios.create({
  baseURL: process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:4000/api",
  headers: { "Content-Type": "application/json" },
  withCredentials: false, // BE usa JWT en header, no cookies
});
NUEVO frontend/src/services/authService.ts

5 métodos, uno por endpoint del BE. Los componentes y hooks nunca conocen URLs ni Axios.

Método Endpoint BE Descripción
authService.registro() POST /auth/registro Crea usuario, devuelve mensaje
authService.login() POST /auth/login Devuelve JWT + datos de usuario
authService.recuperarContrasena() POST /auth/recuperar-contrasena Genera token de recuperación en DB
authService.nuevaContrasena() POST /auth/nueva-contrasena Valida token, actualiza hash bcrypt
authService.verificarEmail() POST /auth/verificar-email Valida token, marca cuenta verificada

3. Archivos modificados

MODIFICADO frontend/src/lib/auth.ts

Tres cambios principales:

  • Extensión de tipos NextAuth — se añaden id, rol y backendToken a la interfaz Session y JWT.
  • CredentialsProvider — nuevo provider que llama a authService.login() en authorize(). Propaga el token JWT del backend a la sesión de NextAuth.
  • pages.newUser cambiado de /registro a /completar-perfil — los usuarios nuevos de Google OAuth van al onboarding. 
// Extensión de tipos
declare module "next-auth" {
  interface Session {
    user: DefaultSession["user"] & {
      id?: string;
      rol?: string;
      backendToken?: string;
    };
  }
}

// CredentialsProvider — llama al BE real
CredentialsProvider({
  async authorize(credentials) {
    const { token, usuario } = await authService.login({
      correo: credentials.correo,
      contrasena: credentials.contrasena,
    });
    return { id: usuario.id, backendToken: token, ... };
  }
})
MODIFICADO formularioRegistro.tsx — función alEnviar
  • Sustituido setTimeout por authService.registro()
  • Error 409 ("Este correo ya está registrado") → mensaje específico al usuario
  • Redirige a /verificar-email/pendiente?email=... tras éxito
  • confirmarContrasena no se envía al BE — ya validado por Zod en el cliente
MODIFICADO formularioLogin.tsx — función alEnviar
  • Sustituido setTimeout por signIn("credentials", { redirect: false })
  • Si resultado.ok → router.push("/home")
  • Si resultado.error === "Debes verificar tu correo..." → mensaje específico
  • Cualquier otro error → mensaje genérico de credenciales incorrectas
  • No importa authService directamente — el login pasa por NextAuth
MODIFICADO formularioRecuperarContrasena.tsx — función alEnviar
  • Sustituido setTimeout por authService.recuperarContrasena()
  • El BE siempre devuelve 200 (nunca revela si el correo existe) — cualquier error es de red
  • Redirige a /recuperar-contrasena/pendiente?email=... tras éxito
MODIFICADO formularioNuevaContrasena.tsx — función alEnviar
  • Sustituido setTimeout por authService.nuevaContrasena({ token, contrasena })
  • token llega como prop desde la página padre (query string ?token=...)
  • Error 400 → muestra mensaje del backend ("Token inválido o expirado")

6. Limitaciones conocidas hasta Fase 6

🔒 Login con email/contraseña → 403 hasta verificar manualmente

El endpoint POST /api/auth/login comprueba cuentaVerificada: true antes de devolver el token. Como Resend (emails) se activa en Fase 6, los usuarios nuevos no reciben el correo de verificación. Para probar el login durante desarrollo: 

// En MongoDB Atlas → colección usuarios → editar documento:
{ cuentaVerificada: true }

El login con Google OAuth no tiene esta restricción y funciona sin cambios.

📧 Recuperar contraseña / Verificar email → token en DB, sin email

El token se genera y guarda en MongoDB correctamente, pero no llega al usuario por correo hasta Fase 6. Para probar nueva-contrasena durante desarrollo, recupera el token directamente de la colección tokens en Atlas.

👤 formularioCompletarPerfil.tsx — mock hasta Fase 5

El formulario de onboarding (alérgenos + dietas) no llama aún al backend. Se implementará cuando exista usuariosService.actualizarPerfil() en Fase 5.
