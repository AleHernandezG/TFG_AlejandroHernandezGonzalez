Optimización de Rendimiento — PERF-SSR-001

Sprint 6 · 2026-06-01 · Estado: ✅ Completado

Contexto y objetivo

Next.js 14 App Router proporciona un mecanismo nativo de loading states: cuando se coloca un archivo loading.tsx junto a page.tsx, el framework lo envuelve automáticamente en un Suspense boundary. El usuario ve el skeleton inmediatamente mientras la página realiza la carga inicial, eliminando pantallas en blanco.

Las dos rutas con mayor tiempo de carga percibida son /home (renderiza CSR con TanStack Query) y /recetas/[id] (RSC con force-dynamic + fetch de MongoDB).

Archivos creados

ArchivoDescripción
app/(main)/home/loading.tsx Skeleton de la vista home: header con título + chips de filtro + 3 tarjetas de receta de altura 420px
app/(main)/recetas/[id]/loading.tsx Skeleton de detalle: hero 400px + cabecera rounded-t-[2rem] + título + descripción + avatar + pills de meta + lista de ingredientes

Análisis de rutas

RutaTipo de renderMejora aplicada
/home Server Component estático + Client Components CSR loading.tsx con skeleton — el shell RSC ya era estático
/recetas/[id] force-dynamic — SSR en cada request loading.tsx con skeleton que coincide con la estructura real de la página
/despensa CSR puro (Client Component) Ya tiene skeletons internos — no requiere loading.tsx
/perfil CSR puro Ya óptimo

Cómo funciona el mecanismo

// app/(main)/recetas/[id]/page.tsx  →  tiene force-dynamic
// app/(main)/recetas/[id]/loading.tsx →  Next.js lo envuelve automáticamente:

// Equivalente interno de Next.js:
<Suspense fallback={<Loading />}>
  <Page />
</Suspense>

El archivo loading.tsx se activa tanto en la navegación inicial como en las navegaciones client-side con <Link> cuando la ruta utiliza force-dynamic o tiene latencia de red.

Cómo verificar

En Chrome DevTools → Network → throttling a "Slow 3G". Navegar a /home o a /recetas/[id] — el skeleton aparece durante ~2-5 segundos antes del contenido real.
