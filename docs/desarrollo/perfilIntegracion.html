Arquitectura del módulo de perfil

Patrón de capas BE

usuarios.routes.ts → usuariosController.ts → usuariosService.ts → usuarioRepository.ts → usuarioMongo.ts

Patrón de capas FE

contenidoPerfil.tsx (CC) → useMiPerfil / useActualizarPreferencias → perfilService.ts → apiClient.ts → BE /api/usuarios/me
dialogCambiarContrasena.tsx (CC) → useCambiarContrasena → perfilService.ts → BE /api/usuarios/me/contrasena

Fuentes de datos del perfil

  • NextAuth session — nombre, email, image (foto): ya disponibles en useSession(), no se refetchen del BE
  • GET /api/usuarios/me — alergias[], preferencias[], proveedor: datos que no están en la sesión y necesitan BE
  • Zustand perfilStore — permisos (ubicacion, camara, notificaciones): estado local de UI, no persiste en BE

Middleware de autenticación

  • requerirAuth — todos los endpoints de perfil requieren token válido → 401 si ausente o inválido
  • req.usuario.id — identificador extraído del JWT, usado para aislar datos del usuario autenticado

Mapeo de campos BE ↔ FE

El modelo MongoDB almacena alergias[] (para los alérgenos) y preferencias[] (para las dietas). El FE usa los nombres semánticamente correctos para cada concepto: alergenos y dietas. El service BE gestiona el mapeo al leer y escribir.

backend/src/services/usuariosService.ts — lógica de negocio (PERF-BE-001–003)

import bcrypt from "bcryptjs"
const SALT_ROUNDS = 10

// PERF-BE-001
async function obtenerPerfil(usuarioId: string) {
  const usuario = await usuarioRepository.buscarPerfilPorId(usuarioId)
  if (!usuario) throw new ErrorHttp(404, "Usuario no encontrado")
  return {
    nombre: usuario.nombre,
    correo: usuario.correo,
    foto: usuario.foto ?? null,
    alergias: usuario.alergias ?? [],
    preferencias: usuario.preferencias ?? [],
    proveedor: usuario.proveedor,
  }
}

// PERF-BE-002
async function cambiarContrasena(usuarioId: string, contrasenaActual: string, contrasenaNueva: string) {
  const usuario = await usuarioRepository.buscarPorIdConContrasena(usuarioId)
  if (!usuario) throw new ErrorHttp(404, "Usuario no encontrado")
  if (usuario.proveedor !== "local") throw new ErrorHttp(400, "Los usuarios de Google no pueden cambiar la contraseña")
  const coincide = await bcrypt.compare(contrasenaActual, usuario.contrasena!)
  if (!coincide) throw new ErrorHttp(400, "La contraseña actual es incorrecta")
  const hash = await bcrypt.hash(contrasenaNueva, SALT_ROUNDS)
  await usuarioRepository.actualizarContrasena(usuarioId, hash)
}

// PERF-BE-003
async function actualizarPreferencias(usuarioId: string, dietas: string[], alergenos: string[]) {
  const actualizado = await usuarioRepository.actualizarPreferencias(usuarioId, {
    preferencias: dietas,
    alergias: alergenos,
  })
  if (!actualizado) throw new ErrorHttp(404, "Usuario no encontrado")
  return {
    nombre: actualizado.nombre, correo: actualizado.correo, foto: actualizado.foto ?? null,
    alergias: actualizado.alergias ?? [], preferencias: actualizado.preferencias ?? [],
    proveedor: actualizado.proveedor,
  }
}

frontend/src/services/perfilService.ts — capa HTTP (PERF-FE-001)

Nuevo fichero. Encapsula todas las llamadas HTTP al módulo de perfil.

export interface PerfilRespuesta {
  nombre: string
  correo: string
  foto: string | null
  alergias: string[]
  preferencias: string[]
  proveedor: 'local' | 'google'
}

export const perfilService = {
  async getMiPerfil(token: string): Promise<PerfilRespuesta> {
    const { data } = await apiClient.get('/usuarios/me', {
      headers: { Authorization: `Bearer ${token}` },
    })
    return data
  },

  async cambiarContrasena(token: string, contrasenaActual: string, contrasenaNueva: string): Promise<void> {
    await apiClient.put('/usuarios/me/contrasena',
      { contrasenaActual, contrasenaNueva },
      { headers: { Authorization: `Bearer ${token}` } }
    )
  },

  async actualizarPreferencias(token: string, dietas: string[], alergenos: string[]): Promise<PerfilRespuesta> {
    const { data } = await apiClient.put('/usuarios/me/preferencias',
      { dietas, alergenos },
      { headers: { Authorization: `Bearer ${token}` } }
    )
    return data
  },
}

Hook / FunciónTipoDescripción

Optimistic update en useActualizarPreferencias

onMutate: async ({ dietas, alergenos }) => {
  await queryClient.cancelQueries({ queryKey: QUERY_KEY })
  const anterior = queryClient.getQueryData<PerfilRespuesta>(QUERY_KEY)
  queryClient.setQueryData<PerfilRespuesta>(QUERY_KEY, (prev) =>
    prev ? { ...prev, preferencias: dietas, alergias: alergenos } : prev
  )
  return { anterior }
},
onError: (_err, _vars, context) => {
  if (context?.anterior) queryClient.setQueryData(QUERY_KEY, context.anterior)
},
onSuccess: (data) => {
  queryClient.setQueryData(QUERY_KEY, data)
},

Validaciones en el controller

  • cambiarContrasena — contrasenaActual y contrasenaNueva deben ser strings no vacíos; contrasenaNueva.length >= 8 (validación duplicada en FE con Zod)
  • actualizarPreferencias — dietas y alergenos deben ser Array.isArray(); arrays vacíos son válidos (el usuario puede quitar todas sus preferencias)
  • Todos los endpoints retornan 401 automáticamente si el JWT es inválido o ausente (middleware requerirAuth)

Errores del servicio de contraseña

  • 400 — "Los usuarios de Google no pueden cambiar la contraseña" (proveedor !== 'local')
  • 400 — "La contraseña actual es incorrecta" (bcrypt.compare retorna false)
  • 404 — "Usuario no encontrado" (id en JWT no existe en BD)

Flujos de datos

Carga inicial del perfil

contenidoPerfil mounts → useSession() → nombre, email, foto → useMiPerfil() → GET /api/usuarios/me → alergias, preferencias, proveedor → render con datos reales

Actualizar preferencias — optimistic update

  1. Usuario guarda cambios en el dialog de preferencias y alérgenos
  2. onMutate: cancela fetches en vuelo de ['perfil'], actualiza cache inmediatamente
  3. UI refleja los nuevos valores antes de que el BE responda
  4. Mutación: PUT /api/usuarios/me/preferencias con Bearer token
  5. Si éxito → onSuccess: setQueryData con la respuesta del BE (fuente de verdad)
  6. Si error → onError: restaura el estado anterior del cache (rollback)

Cambiar contraseña — flujo de éxito

usuario envía formulario → Zod valida (min 8, letra, número) → PUT /me/contrasena → bcrypt.compare + bcrypt.hash → 200 OK → setExito(true) → pantalla confirmación

Cambiar contraseña — contraseña incorrecta

PUT /me/contrasena → bcrypt.compare → false → 400 "La contraseña actual es incorrecta" → extraerMensajeError(err) → setErrorServidor → mensaje en dialog

Control de visibilidad — usuario Google

useMiPerfil() → proveedor: 'google' → esLocal = false → FilaAjuste "Cambiar contraseña" oculta

PERF-FIX-001 · 2026-05-15 — Dialog preferencias no mostraba chips activos

Síntoma

Al abrir el dialog de preferencias y alérgenos, ningún chip aparecía resaltado aunque el usuario tuviera datos guardados en la BD. El dialog se abría correctamente pero el estado draft se inicializaba siempre con arrays vacíos.

Causa raíz — tres problemas combinados

FicheroProblema
usePerfil.ts refetchOnMount: 'always' sin staleTime: cada vez que ContenidoPerfil montaba, la query se marcaba como stale y relanzaba el fetch. Durante ese refetch perfil volvía a ser undefined momentáneamente, haciendo que dietasActivas = [].
contenidoPerfil.tsx useEffect(() => qc.invalidateQueries(['perfil']), [qc]) invalidaba la query en cada mount, amplificando la ventana de tiempo en que los datos estaban vacíos.
dialogPreferenciasAlergenos.tsx El draft se inicializaba con props dietasActivas/alergenosActivos que llegaban desde el padre. Si el dialog se abría durante el refetch, las props eran [] y el draft quedaba vacío. Aunque el useEffect tenía estas props en sus deps, la dependencia transitiva a través del padre añadía latencia.
perfilService.ts import apiClient from './apiClient' era un import default, pero apiClient es un named export. Error de compilación TS silenciado en desarrollo.

Cambios aplicados

usePerfil.ts — staleTime en lugar de refetchOnMount

// ANTES
return useQuery({
  queryKey: QUERY_KEY,
  queryFn: () => perfilService.getMiPerfil(token),
  enabled: !!token,
  refetchOnMount: 'always',   // ← refetch en cada mount, datos vacíos transitoriamente
})

// DESPUÉS
return useQuery({
  queryKey: QUERY_KEY,
  queryFn: () => perfilService.getMiPerfil(token),
  enabled: !!token,
  staleTime: 5 * 60 * 1000,  // ← cache válido 5 min, datos disponibles inmediatamente
})

contenidoPerfil.tsx — eliminado invalidateQueries en mount

// ELIMINADO — causaba refetch en cada mount
useEffect(() => {
  qc.invalidateQueries({ queryKey: ['perfil'] })

dialogPreferenciasAlergenos.tsx — useMiPerfil directamente en el dialog

El dialog ya no recibe las preferencias como props desde el padre. Lee directamente del cache de TanStack Query mediante useMiPerfil(). TanStack Query deduplica la query: no se hace ninguna llamada HTTP extra.

// ANTES — props desde el padre (podían llegar vacías durante refetch)
interface Props {
  abierto: boolean
  onCerrar: () => void
  dietasActivas: string[]    // ← eliminado
  alergenosActivos: string[] // ← eliminado
}

useEffect(() => {
  if (abierto) {
    setDietasDraft(dietasActivas)
    setAlergenosDraft(alergenosActivos)
    setErrorServidor(null)
  }
}, [abierto, dietasActivas, alergenosActivos])

// DESPUÉS — datos del cache, acceso directo y sin latencia
interface Props {
  abierto: boolean
  onCerrar: () => void
}

const { data: perfil } = useMiPerfil()  // cache hit, sin fetch extra

useEffect(() => {
  if (abierto) {
    setDietasDraft(perfil?.preferencias ?? [])
    setAlergenosDraft(perfil?.alergias ?? [])
    setErrorServidor(null)
  }
}, [abierto, perfil])  // deps limpias, perfil es la fuente de verdad

Decisiones de tipado destacadas

  • proveedor: 'local' | 'google' — union type en el FE para que TypeScript pueda estrechar el tipo y el IDE ayude con el control de visibilidad
  • foto: string | null — nullable explícito; el operador ?? del service BE garantiza que nunca se envíe undefined
  • context: { anterior: PerfilRespuesta | undefined } en useMutation — tipado del contexto del optimistic update para que onError pueda hacer rollback seguro
  • buscarPorIdConContrasena usa select("+contrasena") — el + es necesario porque el campo tiene select: false en el schema Mongoose; sin él, usuario.contrasena sería undefined
