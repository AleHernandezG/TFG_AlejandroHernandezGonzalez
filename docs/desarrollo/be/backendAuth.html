1. Visión general — ¿qué hace este backend?

El backend es una API REST: un servidor que escucha peticiones HTTP y devuelve datos en formato JSON. El frontend (Next.js) le envía peticiones y él responde.

Este sprint implementa todo lo relacionado con autenticación:

Endpoint¿Qué hace?
POST /api/auth/registroCrea una cuenta nueva con email y contraseña
POST /api/auth/loginInicia sesión y devuelve un token de acceso (JWT)
POST /api/auth/verificar-emailConfirma que el email del usuario es real
POST /api/auth/recuperar-contrasenaGenera un enlace para cambiar la contraseña
POST /api/auth/nueva-contrasenaEstablece la nueva contraseña usando el enlace

El servidor arranca en localhost:4000 en desarrollo. Hay también un endpoint de diagnóstico: GET /api/health → devuelve {"estado":"ok"}.

3. El patrón de capas — por qué el código está dividido así

Cuando llega una petición al servidor, no va directamente a MongoDB. Pasa por varias capas en orden. Cada capa tiene una única responsabilidad. Esto hace que el código sea más fácil de mantener y cambiar.

Route
→
Define la URL. Aplica middlewares.
Controller
→
Recibe la petición. Llama al service. Devuelve JSON.
Service
→
Las reglas de la app. ¿Puede registrarse? ¿Es válida la contraseña?
Repository
→
Toda la comunicación con MongoDB. Buscar, crear, actualizar.
MongoDB
→
La base de datos en la nube (Atlas).
¿Por qué no acceder a MongoDB directamente desde el controller? Porque si mañana cambiamos MongoDB por PostgreSQL, solo tenemos que tocar los repositories. El resto del código no sabe ni nota el cambio. Separación de responsabilidades.

Ejemplo práctico: cuando el usuario pulsa "Registrarse":

  1. auth.routes.ts — recibe POST /api/auth/registro, valida el body con Zod
  2. authController.ts — llama a authService.registrarse()
  3. authService.ts — comprueba que el correo no existe, hashea la contraseña, crea el token
  4. usuarioRepository.ts — ejecuta Usuario.create(datos) en MongoDB
  5. tokenRepository.ts — ejecuta Token.create(datos) en MongoDB
  6. La respuesta sube de vuelta: 201 { mensaje: "Revisa tu correo..." }

4. Bloque 1 — Arranque del servidor

server.ts — el punto de entrada

Es el primer fichero que se ejecuta. Hace dos cosas en orden:

  1. Conecta con MongoDB (conectarDB())
  2. Arranca el servidor HTTP en el puerto 4000
import "dotenv/config";          // carga el .env en process.env
import app from "./app";
import { conectarDB } from "./lib/db";

async function arrancar() {
  await conectarDB();            // primero conecta a la BD
  app.listen(4000, () => {
    console.log("🚀 Servidor en http://localhost:4000");
  });
}

arrancar();

app.ts — configuración de Express

Aquí se configura todo lo que Express hace con cada petición antes de llegar a las rutas:

Middleware¿Qué hace?
helmet()Añade cabeceras HTTP de seguridad automáticamente (protege contra ataques comunes)
morgan("dev")Muestra en consola cada petición recibida: método, URL, status, tiempo
cors({...})Solo acepta peticiones del frontend (localhost:3000). Bloquea otros orígenes.
express.json()Transforma el body JSON de la petición en un objeto JavaScript accesible en req.body

lib/db.ts — conexión a MongoDB

Usa Mongoose para conectarse a MongoDB Atlas usando la URI del .env. Si la conexión falla, el proceso termina con process.exit(1) — no tiene sentido arrancar un servidor de datos sin base de datos.

5. Bloque 2 — Modelos de datos (MongoDB)

Los modelos definen la estructura de los documentos que se guardan en MongoDB. Son como plantillas: "un usuario siempre tiene nombre, correo, rol...". Se definen con Mongoose (librería que conecta Node.js con MongoDB).

usuario.model.ts — colección usuarios

CampoTipoDescripción
nombreStringNombre del usuario. Entre 2 y 50 caracteres.
correoString (único)Email. Índice único — no puede haber dos iguales. Siempre en minúsculas.
contrasenaString (oculto)Hash bcrypt. Tiene select: false — no se devuelve en queries por defecto. Nunca en texto plano.
fotoString (URL)URL de Cloudinary. Opcional. Se asigna en Fase 6.
rolenum"usuario" o "admin". Por defecto "usuario".
cuentaVerificadaBooleanEmpieza en false. Se pone a true al verificar el email.
proveedorenum"local" (registro con email) o "google" (OAuth).
googleIdStringSolo para usuarios de Google. Es su ID en Google.
alergiasString[]IDs de alérgenos seleccionados en /completar-perfil.
preferenciasString[]IDs de dietas seleccionadas en /completar-perfil.
fechaRegistroDateAutomático al crear. No editable.
¿Qué es select: false? Cuando haces Usuario.findOne({ correo }), MongoDB devuelve todos los campos excepto los marcados con select: false. Así la contraseña nunca aparece por accidente en una respuesta. Para obtenerla explícitamente hay que usar .select("+contrasena") — solo en el login.

token.model.ts — colección tokens

Los tokens son códigos temporales que se envían por email. Sirven para dos cosas: verificar que el email es real, o permitir cambiar la contraseña.

CampoTipoDescripción
userIdObjectIdReferencia al usuario al que pertenece este token.
tokenStringCadena aleatoria de 64 caracteres hex. Único en toda la colección.
tipoenum"verificacion" (24h) o "recuperacion" (1h).
expiraDateFecha de caducidad. MongoDB tiene un TTL index aquí — borra automáticamente el documento cuando llega esa fecha.
usadoBooleanUna vez usado, se marca como true para que no se pueda reutilizar.
¿Qué es un TTL index? Es un índice especial de MongoDB que actúa como un temporizador automático. Cuando el campo expira llega al pasado, MongoDB borra el documento solo. No hay que ejecutar ningún proceso de limpieza — MongoDB lo hace en segundo plano. Es como una fecha de caducidad en un yogur: pasada esa fecha, desaparece.

6. Bloque 3 — Repositorios

Los repositorios son la única capa que habla con MongoDB. Son objetos con métodos simples y específicos. El service los llama pero no sabe cómo están implementados — solo sabe qué devuelven.

usuarioRepository.ts

export const usuarioRepository = {
  crear: (datos) => Usuario.create(datos),

  buscarPorCorreo: (correo) =>
    Usuario.findOne({ correo }),                  // SIN contraseña

  buscarPorCorreoConContrasena: (correo) =>
    Usuario.findOne({ correo }).select("+contrasena"), // CON contraseña (solo login)

  existePorCorreo: async (correo) =>
    !!(await Usuario.exists({ correo })),         // devuelve true/false

  actualizarVerificacion: (id) =>
    Usuario.findByIdAndUpdate(id, { cuentaVerificada: true }),

  actualizarContrasena: (id, contrasenaHash) =>
    Usuario.findByIdAndUpdate(id, { contrasena: contrasenaHash }),
};

tokenRepository.ts

export const tokenRepository = {
  crear: (datos) => Token.create(datos),

  buscarPorToken: (token) =>
    Token.findOne({ token, usado: false }),  // solo tokens no usados

  invalidar: (id) =>
    Token.findByIdAndUpdate(id, { usado: true }),
};

7. Bloque 4 — Utilidades (JWT y Zod)

lib/jwt.ts — tokens de sesión

JWT (JSON Web Token) es un estándar para crear tokens de sesión firmados. Cuando el usuario hace login correctamente, el servidor le da un JWT. En cada petición posterior, el frontend envía ese JWT en la cabecera HTTP — el servidor lo verifica y sabe quién es sin consultar la base de datos.

¿Cómo funciona un JWT? Tiene 3 partes separadas por puntos: header.payload.signature
— Header: tipo de token y algoritmo de firma (HS256)
— Payload: datos del usuario (id, correo, rol)
— Signature: firma digital con el JWT_SECRET

Cualquiera puede leer el payload (no tiene datos sensibles), pero solo el servidor puede crear tokens válidos porque es el único que conoce el JWT_SECRET. 
// Crear un token al hacer login:
firmarToken({ id: "abc123", correo: "user@cookr.es", rol: "usuario" })
// → "eyJhbGci......" (cadena larga)

// Verificar el token que envía el frontend:
verificarToken("eyJhbGci......")
// → { id: "abc123", correo: "user@cookr.es", rol: "usuario" }

lib/validadores.ts — schemas Zod

Zod es una librería de validación de datos. Define qué forma debe tener el body de cada endpoint antes de procesarlo. Si el body no cumple el schema, el middleware devuelve 400 automáticamente — el service nunca llega a ejecutarse.

Es la segunda barrera de validación (la primera es el frontend con React Hook Form).

SchemaCampos que valida
esquemaRegistronombre (2-50 chars), correo (email válido), contraseña (min 8, 1 letra, 1 número)
esquemaLogincorreo (email), contraseña (no vacía)
esquemaRecuperarcorreo (email)
esquemaNuevaContrasenatoken (no vacío), contraseña (min 8, 1 letra, 1 número)
esquemaVerificarEmailtoken (no vacío)

8. Bloque 5 — Middlewares

Un middleware es una función que se ejecuta entre que llega la petición y que llega al controller. Puede leer la petición, modificarla, o cortarla con un error. Express los encadena en orden.

validarBody.ts — validación Zod automática

Es un middleware genérico: recibe un schema Zod y devuelve un middleware de Express. Si el body no pasa la validación, responde 400 con los errores detallados. Si pasa, reemplaza req.body con los datos ya transformados (ej: correo en lowercase) y llama a next() para continuar. 

// Ejemplo de error que devuelve si el correo es inválido:
{
  "error": "Datos inválidos",
  "errores": [
    { "campo": "correo", "mensaje": "Correo no válido" }
  ]
}

autenticacion.ts — JWT middleware (requerirAuth)

Protege rutas que requieren estar logueado. Lee la cabecera Authorization: Bearer TOKEN, verifica la firma del JWT y adjunta el usuario a req.usuario para que los controllers puedan acceder a él. Si el token es inválido o falta, devuelve 401.

En este sprint no hay rutas protegidas aún — se usará a partir del Sprint 3.

errores.ts — error handler global

En Express, un middleware con 4 parámetros (err, req, res, next) es especial: captura cualquier error que ningún otro código haya manejado y devuelve 500. Evita que el servidor se caiga o devuelva mensajes de error de Node.js sin format.

9. Bloque 6 — Service, Controller y Routes

authService.ts — las reglas de negocio

Es el corazón del backend. Contiene toda la lógica: qué puede hacer el usuario, qué condiciones deben cumplirse, qué pasos hay que ejecutar en orden. No sabe nada de HTTP (no conoce req ni res). Solo recibe datos, hace cosas, devuelve resultados o lanza errores.

Método¿Qué hace?
registrarse()Comprueba que el correo no existe. Hashea contraseña. Crea usuario. Crea token de verificación.
iniciarSesion()Busca el usuario. Compara contraseña con bcrypt. Verifica que la cuenta está verificada. Devuelve JWT.
verificarEmail()Busca el token. Comprueba que no está usado ni expirado. Marca usuario como verificado. Invalida token.
solicitarRecuperacion()Busca el usuario. Crea token de recuperación 1h. Respuesta genérica (no revela si existe el correo).
restablecerContrasena()Valida token de recuperación. Hashea nueva contraseña. Actualiza usuario. Invalida token.

authController.ts — thin controller

El controller es deliberadamente fino (thin): no tiene lógica de negocio. Solo recibe el req, llama al método correcto del service y devuelve el resultado como JSON. Si el service lanza un error, lo captura y devuelve el status HTTP adecuado. 

async registro(req, res) {
  try {
    const resultado = await authService.registrarse(req.body);
    res.status(201).json(resultado);
  } catch (error) {
    manejarError(res, error);  // usa el .status del error si existe
  }
}

auth.routes.ts — las URLs

Define qué middleware y qué controller se ejecutan para cada URL. El middleware validarBody siempre va antes del controller. 

router.post("/registro",             validarBody(esquemaRegistro),   authController.registro);
router.post("/login",                validarBody(esquemaLogin),      authController.login);
router.post("/verificar-email",      validarBody(esquemaVerificar),  authController.verificarEmail);
router.post("/recuperar-contrasena", validarBody(esquemaRecuperar),  authController.recuperarContrasena);
router.post("/nueva-contrasena",     validarBody(esquemaNueva),      authController.nuevaContrasena);

10. Los 5 endpoints — flujo completo

POST /api/auth/registro

PasoQué ocurre
1Zod valida { nombre, correo, contrasena }
2Se comprueba que el correo no existe en MongoDB
3Se hashea la contraseña con bcrypt (10 rondas)
4Se crea el documento Usuario en MongoDB con cuentaVerificada: false
5Se genera un token aleatorio de 64 chars hex y se guarda en Token (expira en 24h)
6TODO Fase 6: enviar email con ese token
7Responde 201 { mensaje: "Revisa tu correo..." }

POST /api/auth/login

PasoQué ocurre
1Zod valida { correo, contrasena }
2Se busca el usuario por correo, incluyendo la contraseña (.select("+contrasena"))
3Si no existe → 401 Credenciales incorrectas (mismo error para no revelar si existe)
4bcrypt.compare() compara la contraseña del body con el hash guardado
5Si no coincide → 401 Credenciales incorrectas
6Si cuentaVerificada === false → 403 Debes verificar tu correo
7Se firma un JWT con { id, correo, rol } y expira en 7 días
8Responde 200 { token: "JWT...", usuario: { id, nombre, correo, foto, rol } }

POST /api/auth/verificar-email

PasoQué ocurre
1Zod valida que llega un campo token
2Se busca el token en MongoDB (usado: false)
3Si no existe o no es de tipo "verificacion" → 400
4Si expira < ahora → 400 El enlace ha expirado
5Se actualiza el usuario: cuentaVerificada: true
6Se invalida el token: usado: true
7Responde 200 { mensaje: "Email verificado..." }

POST /api/auth/recuperar-contrasena

PasoQué ocurre
1Zod valida el correo
2Se busca el usuario. Si no existe, se responde igual (no se revela que el correo no existe)
3Se genera token de recuperación (expira en 1h) y se guarda
4TODO Fase 6: enviar email con enlace de recuperación
5Responde siempre 200 { mensaje: "Si existe una cuenta..." }
¿Por qué la respuesta es siempre la misma aunque el correo no exista? Es una medida de seguridad. Si dijera "este correo no está registrado", un atacante podría probar correos para descubrir qué usuarios existen en la app. Con la respuesta genérica, no obtiene información útil.

POST /api/auth/nueva-contrasena

PasoQué ocurre
1Zod valida { token, contrasena }
2Se busca el token de recuperación (usado: false)
3Se verifica que es de tipo "recuperacion" y no está expirado
4Se hashea la nueva contraseña con bcrypt
5Se actualiza la contraseña del usuario en MongoDB
6Se invalida el token
7Responde 200 { mensaje: "Contraseña actualizada..." }

11. Conceptos de seguridad

bcryptjs — hash de contraseñas

Las contraseñas nunca se guardan en texto plano. Se usa bcrypt, un algoritmo de hash diseñado específicamente para contraseñas. Tiene dos características clave:

  • Es lento a propósito: las 10 rondas hacen que hashear tarde ~100ms. Eso hace que un ataque de fuerza bruta sea inviable (millones de intentos tardarían años).
  • Tiene "salt" incorporado: aunque dos usuarios tengan la misma contraseña, sus hashes serán distintos porque bcrypt añade un valor aleatorio antes de hashear.
// Guardar contraseña:
const hash = await bcrypt.hash("miContrasena123", 10);
// → "$2b$10$X7k3mP..." (cadena irreversible)

// Verificar en el login:
const valida = await bcrypt.compare("miContrasena123", hash);
// → true ✅

JWT_SECRET — la llave del servidor

Es una cadena aleatoria larga que solo conoce el servidor. Se usa para firmar los tokens JWT. Si alguien modifica el payload del token (ej: cambia su rol a "admin"), la firma no coincidirá y el servidor lo rechazará. Está en el .env y nunca debe publicarse.

bcryptjs vs bcrypt

Usamos bcryptjs (JavaScript puro) en lugar de bcrypt (que requiere compilación nativa de C++). En Windows, compilar módulos nativos puede dar problemas. bcryptjs es compatible, más fácil de instalar y suficientemente rápido para un TFG.
