2. Flujo: usuario local (email + contraseña)

Los usuarios locales deben verificar su correo electrónico antes de poder iniciar sesión. Solo después de verificar se les permite entrar y completar su perfil.
1. REGISTRO
   → /registro — formulario nombre + correo + contraseña
   → POST /api/auth/registro
      — hashea contraseña con bcrypt (10 rounds)
      — crea usuario: proveedor:"local", cuentaVerificada:false, perfilCompleto:false
      — crea token de verificación (hex 32 bytes, TTL 24h) en colección tokens
      — TODO Fase 6: envía email con Resend (URL: /verificar-email?token=xxx)
   → redirige a /verificar-email/pendiente?email=...

2. VERIFICACIÓN
   → usuario hace clic en el enlace del email
   → /verificar-email?token=xxx — llama POST /api/auth/verificar-email ← CORREGIDO (era mock)
      — valida token: existe, tipo "verificacion", no expirado
      — actualiza usuario: cuentaVerificada:true
      — invalida token (usado:true); MongoDB TTL lo eliminará al expirar
   → muestra "¡Correo verificado!" con botón "Iniciar sesión" → /login

3. LOGIN
   → /login — formulario correo + contraseña
   → NextAuth signIn("credentials") → authorize() → POST /api/auth/login
      — comprueba correo, contraseña (bcrypt compare), cuentaVerificada
      — devuelve: { token, usuario, perfilCompleto }
      — callback jwt almacena backendToken, rol, perfilCompleto en el JWT de NextAuth
   → formularioLogin llama getSession() y hace router.push(perfilCompleto ? "/home" : "/completar-perfil")
   (el middleware refuerza esta lógica: cualquier ruta protegida sin perfil → /completar-perfil)

4. COMPLETAR PERFIL
   → completar-perfil/page.tsx (Server Component)
      — sin sesión → redirect /login
      — perfilCompleto === true → redirect /home (usuario volviendo)
      — perfilCompleto === false → muestra <FormularioCompletarPerfil>
   → usuario selecciona alergias y preferencias → "Listo"
   → POST /api/auth/completar-perfil (Authorization: Bearer backendToken)
      — requerirAuth verifica JWT → extrae req.usuario.id
      — actualiza usuario: alergias, preferencias, perfilCompleto:true
   → cliente llama update({ perfilCompleto: true }) — refresca el JWT de NextAuth
   → router.push("/home")

5. LOGINS POSTERIORES
   → mismos pasos 3-4, pero perfilCompleto === true
      — formularioLogin redirige directamente a /home (via getSession())
      — Si el usuario accede directamente a cualquier ruta protegida, el middleware lo deja pasar
      — Si intenta entrar a /completar-perfil, el middleware lo redirige a /home

3. Flujo: usuario Google OAuth

Los usuarios de Google tienen cuentaVerificada: true automáticamente (Google ya lo garantiza). No pasan por el flujo de verificación de correo. Pero sí deben completar su perfil la primera vez.
1. INICIO DE SESIÓN
   → usuario pulsa "Continuar con Google" en /login o /registro
   → signIn('google', { callbackUrl: '/completar-perfil' })
   → NextAuth redirige a Google OAuth
   → Google autentica → devuelve a NextAuth con perfil: { googleId, email, name, image }

2. CALLBACK JWT (servidor — NextAuth)
   → NextAuth dispara callback jwt con account.provider === "google"
   → Llama POST /api/auth/google (fetch server-side)
      con { googleId, correo, nombre, foto }

   El backend ejecuta esta lógica:
      ① busca por googleId → usuario ya vinculado
      ② si no → busca por correo → cuenta local preexistente con mismo email
         → si encuentra: vincularGoogle() — añade googleId y foto si no tenía
      ③ si no → crear(): proveedor:"google", cuentaVerificada:true, perfilCompleto:false
      — firma JWT del backend
      — devuelve { token, usuario, perfilCompleto }

   → callback jwt almacena backendToken, rol, perfilCompleto

3. REDIRECT A /completar-perfil
   → NextAuth redirige al callbackUrl → /completar-perfil
   → page.tsx (Server Component): comprueba session.user.perfilCompleto
      — nuevo usuario: false → muestra formulario
      — usuario volviendo: true → redirect a /home

4. COMPLETAR PERFIL (mismo flujo que local)
   → POST /api/auth/completar-perfil con Bearer backendToken
   → update({ perfilCompleto: true }) + router.push("/home")

4. Modelo MongoDB — todos los campos

Colección: usuarios

Campo Tipo Default Cuándo se rellena Por quién
nombre String — Registro (local o Google) crear()
correo String — Registro (local o Google) crear()
contrasena String (select:false) — Solo registro local (bcrypt hash) crear(), actualizarContrasena()
foto String? — Google: en el momento de crear/vincular. Local: pendiente Fase 4 (ajustes de perfil) crear(), vincularGoogle()
rol "usuario" | "admin" "usuario" Siempre por defecto Schema Mongoose
cuentaVerificada Boolean false Local: tras verificar email. Google: true en el momento de crear actualizarVerificacion(), crear({ cuentaVerificada: true })
perfilCompleto ★ nuevo Boolean false Cuando el usuario guarda alergias y preferencias en /completar-perfil completarPerfil()
proveedor "local" | "google" — Registro crear()
googleId String? — Solo usuarios Google (o local que vincula Google) crear(), vincularGoogle()
alergias ★ antes sin uso String[] [] Cuando el usuario completa el perfil completarPerfil()
preferencias ★ antes sin uso String[] [] Cuando el usuario completa el perfil completarPerfil()
fechaRegistro Date Date.now Siempre en el momento de crear Schema Mongoose

Colección: tokens

Campo Tipo Default Cuándo se rellena
userId ObjectId → Usuario — Al crear token de verificación o recuperación
token String (único) — Cadena hex aleatoria de 32 bytes
tipo "verificacion" | "recuperacion" — Según el contexto de uso
expira Date — Verificación: +24h. Recuperación: +1h
usado Boolean false Se pone a true al validar el token (invalidar())
creadoEn Date Date.now Automático en el momento de crear
TTL automático: La colección tokens tiene un índice TTL sobre el campo expira (expireAfterSeconds: 0). MongoDB elimina el documento automáticamente cuando la fecha expira pasa, sin necesidad de limpieza manual.

5. Backend — archivos modificados

5.1 — repositories/usuarioRepository.ts

Problema anterior

La interfaz DatosCrearUsuario no incluía foto ni cuentaVerificada, por lo que TypeScript rechazaba pasarlos al crear un usuario de Google. Los campos alergias y preferencias existían en el schema pero no había ningún método para escribirlos.

Solución

// ANTES
interface DatosCrearUsuario {
  nombre: string
  correo: string
  contrasena?: string
  proveedor: "local" | "google"
  googleId?: string
}

// DESPUÉS
interface DatosCrearUsuario {
  nombre: string
  correo: string
  contrasena?: string
  foto?: string              // ← nuevo (foto de Google)
  cuentaVerificada?: boolean  // ← nuevo (Google = true en creación)
  proveedor: "local" | "google"
  googleId?: string
}

Métodos nuevos:

  • buscarPorGoogleId(googleId) — para identificar usuarios Google en logins posteriores
  • vincularGoogle(id, { googleId, foto? }) — cuando un usuario local se autentica con el mismo correo en Google
  • completarPerfil(id, { alergias, preferencias }) — escribe alergias, preferencias y pone perfilCompleto: true

5.2 — services/authService.ts

iniciarSesionGoogle (antes: googleOAuth incompleto)

El método anterior solo buscaba por correo y no firmaba ningún JWT ni devolvía token. El nombre tampoco coincidía con lo que llamaba el controlador (iniciarSesionGoogle vs googleOAuth).

Lógica de búsqueda ahora:

① buscarPorGoogleId(googleId)
   → encontrado: usuario ya vinculado, continúa
② si no → buscarPorCorreo(correo)
   → encontrado: cuenta local con mismo email → vincularGoogle() y actualiza
③ si no → crear() con proveedor:"google", cuentaVerificada:true
④ firma JWT del backend y devuelve { token, usuario, perfilCompleto }

iniciarSesion (login local)

Ahora devuelve perfilCompleto: usuario.perfilCompleto junto al token y datos del usuario.

completarPerfil (nuevo)

Recibe userId (del JWT validado por requerirAuth) y llama a usuarioRepository.completarPerfil().

6. Frontend — archivos modificados

6.1 — lib/auth.ts (NextAuth options)

Callback jwt — cómo fluye perfilCompleto

async jwt({ token, user, account, trigger, session }) {

  // ① Credentials — primer login
  if (user && account?.provider === "credentials") {
    token.backendToken = user.backendToken
    token.perfilCompleto = user.perfilCompleto  // viene del backend /auth/login
  }

  // ② Google OAuth — primer login (account presente solo en 1ª vez)
  if (user && account?.provider === "google") {
    const result = await fetch(`${API_URL}/auth/google`, { ... })
    token.backendToken = result.token
    token.perfilCompleto = result.perfilCompleto  // false si es nuevo, true si vuelve
  }

  // ③ update() desde cliente — actualiza perfilCompleto sin re-login
  if (trigger === "update" && session?.perfilCompleto !== undefined) {
    token.perfilCompleto = session.perfilCompleto
  }

  return token
}
¿Por qué fetch() en el callback jwt?
El callback jwt corre en Node.js (servidor). No en el navegador. Por eso se puede llamar al backend con fetch() directamente. El resultado queda guardado en el JWT encriptado de NextAuth y no vuelve a ejecutarse hasta que el token expira o se llama a update().

6.4 — app/verificar-email/contenidoVerificacion.tsx

Mock reemplazado (decisión deliberada): El setTimeout era un placeholder de diseño — mostraba "éxito" en 1.5s sin importar el token, pero no verificaba nada en MongoDB. Para verificar de verdad en desarrollo ya existía POST /dev/verificar-usuario.

El mock se ha reemplazado por la llamada real porque:
  1. El backend sí crea el token en MongoDB al registrarse (aunque no envíe el email).
  2. En dev se puede coger ese token de MongoDB Compass y visitar la URL → verifica de verdad.
  3. El shortcut POST /dev/verificar-usuario sigue disponible para saltar el email completamente.
El envío real del email con Resend sigue siendo Fase 6. Lo que cambia es que la página ya hace la llamada correcta al backend cuando el token llega por URL.

7. Sesión NextAuth — cómo fluye perfilCompleto

JWT de NextAuth (cookie HttpOnly)
 
sub          ← ID del usuario en MongoDB
backendToken ← JWT firmado por el backend Express (para llamadas a la API)
rol          ← "usuario" | "admin"
perfilCompleto ← boolean — sincronizado con la BD
 
session.user (en componentes)
 
id            ← token.sub
backendToken  ← para adjuntar en Authorization: Bearer ...
rol            ← para permisos de UI
perfilCompleto ← para el guard en /completar-perfil/page.tsx

Flujo de update()

NextAuth v4 no re-ejecuta el callback jwt en cada petición (el token se guarda en cookie y se reutiliza hasta expirar). Para actualizar perfilCompleto sin que el usuario tenga que cerrar y volver a abrir sesión, se usa:

// En el cliente (FormularioCompletarPerfil)
const { data: session, update } = useSession()

await authService.completarPerfil({ alergias, preferencias }, session.user.backendToken)
await update({ perfilCompleto: true })  // ← dispara trigger:"update" en el callback jwt
router.push("/home")

En el callback jwt, cuando trigger === "update", el valor de session.perfilCompleto se copia al token. En el siguiente getServerSession() ya aparece como true.

8. Middleware — protección de rutas

frontend/src/middleware.ts — usa withAuth de NextAuth para interceptar peticiones a las rutas protegidas antes de que lleguen al Server Component.

Rutas protegidas (matcher)

PatrónRuta de ejemplo
/home/:path*/home
/coleccion/:path*/coleccion
/recetas/:path*/recetas/abc123
/completar-perfil/:path*/completar-perfil

Lógica de decisión

Petición a ruta protegida
   → authorized({ token }): ¿existe token NextAuth?
      — NO → NextAuth redirige a /login (configurado en pages.signIn)
      — SÍ → entra en la función middleware(req)
   → ¿token.perfilCompleto === false y ruta ≠ /completar-perfil?
      — SÍ → redirect a /completar-perfil
   → ¿token.perfilCompleto === true y ruta = /completar-perfil?
      — SÍ → redirect a /home
   → Ningún caso → NextResponse.next() (deja pasar)

Código

export default withAuth(
  function middleware(req) {
    const { pathname } = req.nextUrl
    const perfilCompleto = req.nextauth.token?.perfilCompleto

    if (perfilCompleto === false && pathname !== "/completar-perfil")
      return NextResponse.redirect(new URL("/completar-perfil", req.url))

    if (perfilCompleto === true && pathname === "/completar-perfil")
      return NextResponse.redirect(new URL("/home", req.url))

    return NextResponse.next()
  },
  { callbacks: { authorized: ({ token }) => !!token } }
)

export const config = {
  matcher: ["/home/:path*", "/coleccion/:path*", "/recetas/:path*", "/completar-perfil/:path*"]
}
¿Por qué middleware y no solo el Server Component?
completar-perfil/page.tsx también hace el check con getServerSession, pero el middleware actúa antes de renderizar cualquier página — incluso antes de que Next.js ejecute el Server Component. Esto evita flashes de contenido y es la capa correcta para la lógica de acceso en Next.js App Router.
