Helper interno

function extraerMensaje(error: unknown, fallback: string): string {
  if (axios.isAxiosError(error)) return error.response?.data?.error ?? fallback
  return fallback
}

Extrae el mensaje de error del backend (campo error en el body) o devuelve el fallback genérico. Evita que los componentes importen Axios.

formularioLogin.tsx (ejemplo representativo)

Antes — lógica inline
import { signIn, getSession } from "next-auth/react"

const [estadoEnvio, setEstadoEnvio] = useState("idle")
const [mensajeError, setMensajeError] = useState(null)

const alEnviar = async (datos) => {
  setEstadoEnvio("cargando")
  const res = await signIn("credentials", { ...datos, redirect: false })
  if (res?.ok) {
    const session = await getSession()
    router.push(session?.user?.perfilCompleto ? "/home" : "/completar-perfil")
    return
  }
  setMensajeError("Correo o contraseña incorrectos.")
  setEstadoEnvio("error")
}
Después — hook
import { useAuth } from "@/features/auth/hooks"

const { iniciarSesion, cargando, error } = useAuth()

const alEnviar = (datos) =>
  iniciarSesion(datos.correo, datos.contrasena)

💡

Decisión de diseño — por qué un hook y no solo el service

  • El service (authService.ts) solo habla HTTP — no sabe nada de NextAuth, useRouter ni de los mensajes de error específicos para cada flujo.
  • El hook es la capa de orquestación — combina authService + signIn (NextAuth) + router + traducción de errores del backend a mensajes en español para el usuario.
  • Los componentes quedan como renderizadores puros — solo gestionan el estado de UI (mostrar contraseña, exito in-page, cooldown de reenvío) que no tiene sentido en un hook compartido.
  • Sin Zustand — el estado del hook es local a cada formulario. No tiene sentido compartir entre formularios si nunca coexisten en pantalla.
  • Testabilidad — el hook puede testearse con mocks de authService y signIn sin necesidad de montar los formularios completos.

BUG-AUTH-001 — Login con credenciales silenciosamente roto por cookie overflow ✅ Resuelto 2026-06-02

Síntoma

Al intentar iniciar sesión con correo y contraseña, todos los endpoints devolvían 200 (backend login OK, NextAuth callback OK) pero la app se quedaba bloqueada en /login con TypeError: Failed to fetch en el overlay de Next.js. El login con Google funcionaba correctamente.

Diagnóstico

El log del servidor reveló la causa raíz:

POST /api/auth/login 200 335ms - 2015168 bytes

La respuesta del login del backend era de 2 MB. Un login debería pesar 1-2 KB.

La cadena de eventos era:

  1. buscarPorCorreoConContrasena ejecutaba Usuario.findOne({ correo }).select("+contrasena") sin restringir campos — devolvía el documento completo del usuario, incluyendo despensa, seguidores, seguidos y el campo foto con la imagen de perfil en base64 (subida desde la feature de avatar del Sprint 6).
  2. El backend incluía usuario.foto (imagen base64 de ~2 MB) en la respuesta de /api/auth/login.
  3. La función authorize() de NextAuth en lib/auth.ts metía esa imagen directamente en image: usuario.foto, que NextAuth serializa en el JWT y guarda en una cookie.
  4. Las cookies del navegador tienen un límite de ~4 KB. El navegador descartaba la cookie silenciosamente sin error visible.
  5. getSession() devolvía null porque no había cookie de sesión. NextAuth lanzaba internamente un TypeError: Failed to fetch que Next.js mostraba como error no capturado.
  6. La URL seguía en /login porque router.push() nunca se ejecutaba (dependía del resultado de getSession()).

El login con Google no fallaba porque la foto de Google es una URL corta (< 100 bytes), no base64.

Fix — dos cambios

Antes — backend/src/repositories/usuarioRepository.ts
buscarPorCorreoConContrasena: (correo) =>
  Usuario.findOne({ correo })
    .select("+contrasena")
// Devuelve el documento COMPLETO:
// foto (base64), despensa[], seguidores[],
// seguidos[], alergias[], preferencias...
// → 2 MB en respuesta
Después
buscarPorCorreoConContrasena: (correo) =>
  Usuario.findOne({ correo })
    .select(
      "+contrasena nombre correo foto " +
      "rol perfilCompleto cuentaVerificada"
    )
// Solo los 7 campos necesarios para el login
// → respuesta de ~1 KB
Antes — frontend/src/lib/auth.ts (authorize)
return {
  id: usuario.id,
  name: usuario.nombre,
  email: usuario.correo,
  image: usuario.foto ?? null, // base64 → overflow
  backendToken: token,
  rol: usuario.rol,
  perfilCompleto,
}
Después
// Si foto es base64 (data:image/...) no la metemos
// en el JWT — excedería el límite de cookie de 4 KB.
// URLs de CDN/picsum sí se permiten (cortas).
const fotoUrl = usuario.foto &&
  !usuario.foto.startsWith("data:")
    ? usuario.foto
    : null

return {
  id: usuario.id,
  name: usuario.nombre,
  email: usuario.correo,
  image: fotoUrl,
  backendToken: token,
  rol: usuario.rol,
  perfilCompleto,
}

Por qué dos fixes y no uno

El fix del repositorio resuelve el problema de raíz (no traer 2 MB del backend) y mejora el rendimiento. El fix de auth.ts es una capa de defensa adicional: si en el futuro el backend volviera a incluir una foto base64 por cualquier motivo, el JWT no rompería la sesión. Las imágenes de perfil en base64 se siguen mostrando correctamente desde GET /api/usuarios/me, que sí devuelve el campo completo.

Lección

Un findOne() sin .select() en Mongoose devuelve todos los campos del documento. En colecciones que acumulan campos grandes (imágenes base64, arrays de despensa, listas de seguidores) esto puede disparar el tamaño de respuesta varias órdenes de magnitud. Siempre proyectar solo los campos necesarios en queries de autenticación.
