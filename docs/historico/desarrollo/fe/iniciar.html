1. Resumen ejecutivo

La vista /login es la segunda pantalla del flujo de autenticación de Cookr. Permite al usuario identificarse mediante correo electrónico + contraseña o mediante Google OAuth.

El diseño sigue el mismo sistema visual que /registro (referentes: Linear, Spotify, Netflix) con una única variación de composición: el layout split-screen está espejado — el formulario ocupa el panel izquierdo y la imagen el panel derecho, creando simetría visual entre ambas rutas y una sensación de progresión natural para el usuario que navega entre ellas.

Estado: mock (Sprint 1) El envío del formulario simula una latencia de red (1 s) y redirige a /. La integración real con NextAuth CredentialsProvider y el backend se implementará en la Fase 4 (Sprint 9-10).

3. Layout split-screen (espejado)

La página /login es un espejo visual de /registro. Ambas usan el mismo sistema de dos paneles, pero con las posiciones invertidas:

Panel /registro /login
Izquierdo Imagen gastronómica + texto editorial Formulario + fondo oscuro
Derecho Formulario + fondo oscuro Imagen gastronómica + texto editorial
Gradiente de fusión from-transparent to-[var(--auth-dark)] (derecha) from-transparent to-[var(--auth-dark)] (izquierda)
Móvil (< lg) Imagen oculta, formulario pantalla completa Imagen oculta, formulario pantalla completa

Técnica de fusión imagen → panel

El gradiente lateral crea una transición sin corte brusco entre la imagen y el fondo oscuro del formulario. En /login el gradiente apunta hacia la izquierda: 

/* Panel imagen — gradiente izquierdo (fusiona con panel formulario) */
className="absolute inset-y-0 left-0 w-32
           bg-gradient-to-l from-transparent to-[var(--auth-dark)]"
Referentes de diseño Linear, Spotify, Netflix y Vercel usan este patrón split-screen en sus páginas de autenticación. La inversión de paneles entre registro y login es una convención reconocida (ej. Notion, Figma) que transmite al usuario que está en una pantalla distinta sin romper el sistema visual.

Comportamiento responsive

Breakpoint Comportamiento
Mobile (< 1024px) Imagen oculta. Formulario ocupa 100% del ancho con bg-[var(--auth-dark)]
Desktop (≥ 1024px) Formulario izquierda lg:w-1/2, imagen derecha lg:w-1/2
Desktop XL (≥ 1280px) Formulario xl:w-2/5, imagen xl:w-3/5 — imagen gana espacio

4. Esquema Zod — DatosLogin

El esquema de login es deliberadamente minimalista: solo dos campos, sin confirmaciones ni validaciones de complejidad (esas pertenecen al registro). El único requisito de contrasena es que no esté vacía — la validación de credenciales es responsabilidad del backend. 

// features/auth/types/autenticacion.ts

export const esquemaLogin = z.object({
  correo: z.string().email("Introduce un correo electrónico válido").trim(),
  contrasena: z.string().min(1, "Introduce tu contraseña"),
});

export type DatosLogin = z.infer<typeof esquemaLogin>;
Campo Tipo Validación Mensaje de error
correo string Formato email válido "Introduce un correo electrónico válido"
contrasena string No vacía (min 1 carácter) "Introduce tu contraseña"
¿Por qué no validar complejidad en login? En login la contraseña ya existe — no tiene sentido imponer reglas de formato que podrían bloquear a usuarios que se registraron con reglas distintas. Solo validamos que el campo no esté vacío antes de enviar al servidor.

Reutilización de EstadoFormulario

El tipo EstadoFormulario = "idle" | "cargando" | "exito" | "error" definido originalmente para registro es compartido por el formulario de login sin modificación. Evita duplicar tipos para el mismo concepto.

Enlace "¿Olvidaste tu contraseña?"

Se coloca en la misma línea que el label de contraseña usando justify-between, patrón estándar en apps de autenticación (Linear, GitHub, Notion). Tiene tabIndex={-1} para no interrumpir el flujo natural de teclado (Tab) del formulario. 

<div className="flex items-center justify-between">
  <Label htmlFor="contrasena">Contraseña</Label>
  <Link
    href="/recuperar-contrasena"
    className="text-xs text-muted-foreground hover:text-brand"
    tabIndex={-1}
  >¿Olvidaste tu contraseña?</Link>
</div>

7. Estados del formulario

Estado Cuándo ocurre UI resultante
idle Estado inicial / tras limpiar error Formulario normal, botón "Iniciar sesión" activo
cargando Durante el envío (mock o real) Botón deshabilitado + spinner Loader2 + texto "Iniciando sesión…"
error Fallo de red o credenciales incorrectas Banner rojo con AlertCircle + mensaje de error. Botón vuelve a ser clicable
exito Login correcto Redirección inmediata (router.push), no hay estado visual visible

Banner de error

Igual que en registro: aparece sobre el formulario con animación de entrada (opacity 0→1, y -8→0) y tiene role="alert" para lectores de pantalla.

Mensaje de error en login El mensaje es deliberadamente ambiguo: "Correo o contraseña incorrectos". No indica cuál de los dos falla — es una práctica de seguridad estándar que evita que un atacante pueda confirmar si un correo está registrado.

11. Flujo de recuperación de contraseña

Implementado en la misma sesión que el login (Sprint 1, 2026-03-24) como extensión natural del enlace "¿Olvidaste tu contraseña?" de FormularioLogin. El flujo completo consta de 3 vistas + 3 componentes, todos en estado mock. La integración real con Resend y el backend se realiza en Fase 4 + 6.

11.1 Mapa del flujo

/login
  └─ clic "¿Olvidaste tu contraseña?"
       ↓
/recuperar-contrasena           ← formularioRecuperarContrasena.tsx
  └─ introduce email → submit
       ↓
/recuperar-contrasena/pendiente ← tarjetaRecuperacionPendiente.tsx
  └─ (usuario recibe email con link)
       ↓
/nueva-contrasena?token=xxx     ← formularioNuevaContrasena.tsx
  └─ nueva contraseña + confirmar → éxito in-page → "Iniciar sesión"
       ↓
/login

11.4 Esquemas Zod añadidos

// Paso 1 — solicitar recuperación: solo email
export const esquemaRecuperarContrasena = z.object({
  correo: z.string().email("Introduce un correo electrónico válido").trim(),
});

// Paso 3 — nueva contraseña: mismas reglas que registro + refine de coincidencia
export const esquemaNuevaContrasena = z
  .object({
    contrasena: z.string()
      .min(8, "Mínimo 8 caracteres")
      .regex(/[A-Za-z]/, "Debe contener al menos una letra")
      .regex(/[0-9]/, "Debe contener al menos un número"),
    confirmarContrasena: z.string(),
  })
  .refine(d => d.contrasena === d.confirmarContrasena, {
    message: "Las contraseñas no coinciden",
    path: ["confirmarContrasena"],
  });

11.5 Decisiones de diseño destacadas

Token como prop, no como hook

FormularioNuevaContrasena recibe el token como prop desde la página Server Component, que lo lee de searchParams.token. Esto evita usar useSearchParams() en el Client Component y previene el error de Suspense boundary que afecta a /verificar-email.

Éxito in-page en /nueva-contrasena

Tras guardar la contraseña correctamente, en vez de redirigir con router.push, el componente renderiza un estado de éxito en la misma Card (fade in + icono CheckCircle2) con un botón "Iniciar sesión" hacia /login. Evita una redirección extra y permite al usuario leer la confirmación sin prisa.

Cooldown de 60s en reenvío

Igual que TarjetaVerificacionPendiente: el botón se deshabilita 60 segundos tras cada reenvío para evitar spam. El estado se gestiona localmente con useState + useEffect (contador regresivo cada 1s).

Estado: mock en los 3 pasos Ningún correo real se envía. El flujo simula latencia de red (1s) y avanza por las vistas. [AUTH-008] y [AUTH-009] documentan la integración real en Fase 4 + 6.
