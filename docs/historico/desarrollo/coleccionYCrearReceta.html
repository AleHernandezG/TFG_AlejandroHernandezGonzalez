Repository — backend/src/repositories/recetaRepository.ts

Se añadieron 4 métodos nuevos al repositorio existente:

findGuardadas(usuarioId)

Obtiene recetasGuardadas[] del documento Usuario, luego hace un find({ _id: { $in: ids } }) proyectando solo los campos necesarios para la tarjeta de colección.

findPorAutor(usuarioId)

Hace find({ autorId: new ObjectId(userId) }) con sort({ fechaPublicacion: -1 }). Devuelve las recetas propias más recientes primero.

crear(datos, autorId)

Mapea dificultad (facil→Fácil, media→Media, dificil→Difícil), concatena tiempo + unidadTiempo, convierte cantidades string→number. Macros en 0 hasta integración Edamam (Sprint 6).

eliminar(recetaId, usuarioId)

Verifica que el autorId del documento coincide con el usuarioId del token. Lanza Error({ status: 403 }) si no. Lanza 404 si la receta no existe.

Flujos de uso

Flujo: Crear receta

  1. Usuario rellena el formulario multi-step en /crear-receta
  2. Datos se guardan en Zustand (useCrearRecetaStore)
  3. Navega a /crear-receta/revisar — vista previa completa
  4. Pulsa "Publicar receta" → useCrearReceta.publicar()
  5. Hook detecta alérgenos de ingredientes con detectarAlergenos()
  6. Llama a recetasService.crear(datos, token) → POST /api/recetas
  7. BE valida con Zod, guarda en MongoDB, devuelve { id }
  8. Hook limpia el store Zustand y redirige a /coleccion?tab=mis-recetas
  9. La nueva receta aparece en la primera posición de "Mis recetas"

Flujo: Ver colección guardada

  1. Usuario navega a /coleccion
  2. useRecetasGuardadas() llama a GET /api/recetas/guardadas
  3. BE obtiene recetasGuardadas[] del documento Usuario, luego popula los documentos Receta
  4. Mientras carga: skeleton de 4 celdas animate-pulse
  5. Tarjetas aparecen con animación AnimatePresence
  6. Bookmark → desguarda con actualización optimista

Flujo: Eliminar receta propia

  1. Usuario pulsa ··· en una tarjeta de "Mis recetas"
  2. Sheet sube desde abajo con opciones
  3. Pulsa "Eliminar receta" → se abre Dialog de confirmación
  4. Confirma → useEliminarReceta.mutate(recetaId)
  5. BE verifica autorId === usuarioId (403 si no coincide)
  6. Devuelve 204 → setEliminada(true) → tarjeta desaparece
  7. Cache ['coleccion', 'mis-recetas'] se invalida automáticamente

Notas técnicas y decisiones de diseño

Imagen como base64

Para el MVP, las fotos de recetas se envían como cadena base64 en el JSON body y se almacenan directamente en MongoDB como imagenUrl. Esto es funcional pero no escala para imágenes grandes. En Sprint 6 se migrará a Cloudinary con subida directa desde el cliente.

En producción, base64 de una foto (~500KB) equivale a ~700KB de datos en el body JSON. Para el TFG es aceptable; para escalar, usar CDN (Cloudinary/S3).

Macros en 0 (placeholder)

El modelo Mongoose requiere el campo macros. Al crear una receta se guarda { calorias: 0, proteinas: 0, carbos: 0, grasas: 0 }. La integración con Edamam para cálculo nutricional real está planificada para Sprint 6.

Alérgenos detectados en el hook

El hook useCrearReceta llama a detectarAlergenos(ingredientes) antes de enviar al BE. Esto aprovecha el mapa estático de 200+ ingredientes con sus alérgenos EU ya implementado en @/config/ingredientes.ts. El backend no tiene su propia función de detección — valida solo que el campo sea un string[].

Actualización optimista en desguardar

Al pulsar el Bookmark en "Guardadas", la tarjeta desaparece visualmente antes de que el backend confirme. Si la petición falla, el onError del mutation hace rollback (setGuardado(true)) para restaurar el estado visual.

Invalidación de caché tras eliminar

useEliminarReceta invalida ['coleccion', 'mis-recetas'] en onSuccess. Esto provoca un refetch del servidor para mantener consistencia. La tarjeta ya se ha marcado como eliminada localmente (setEliminada(true)) para feedback inmediato.

Dificultad: mapeo FE→BE

El formulario FE usa identificadores sin acentos ('facil', 'media', 'dificil') por compatibilidad con Zod enums y convenciones React. El modelo Mongoose almacena los valores con mayúsculas y acentos ('Fácil', 'Media', 'Difícil'). El mapeo se hace en el repository con MAPA_DIFICULTAD.

✅ TypeScript: tsc --noEmit ejecutado en backend y frontend sin errores. Ambos compilados limpiamente tras todos los cambios del sprint.

Dropdown de ingredientes cortado por overflow-hidden

El <ul> de autocompletado en seccionIngredientes.tsx estaba dentro del div con overflow-hidden del card, lo que lo recortaba visualmente. Se movió fuera del card, como hermano directo del contenedor relative, posicionado con top-12 para quedar justo debajo de la fila del input.

Foto Pexels en vista previa antes de publicar

Se añadió el endpoint GET /recetas/foto-preview?query=xxx (sin auth) que reutiliza buscarFotoPexels() de imagenService.ts. El hook useFotoPexelsPreview(titulo) lo llama desde previsualizacionReceta.tsx cuando no hay foto subida. Muestra "Buscando foto…" mientras carga y la atribución obligatoria de Pexels superpuesta sobre el hero. La ruta se declara antes de /:id para que Express no la capture como parámetro.

Redirect a /crear-receta tras publicar — race condition

router.push() en Next.js App Router es asíncrono: inicia la navegación pero no la completa antes de que React re-renderice. Al llamar limpiar(), datos se pone a null, React re-renderiza síncronamente y el useEffect([datos, router]) de la preview disparaba router.replace('/crear-receta'), ganando la carrera a la navegación correcta.

Fix definitivo: la guardia de redirección sólo debe ejecutarse en el montaje (cuando el usuario navega directamente a /crear-receta/revisar sin datos). Se captura el valor inicial con un useRef(datos) y las deps del efecto ya no incluyen datos: 

const datosAlMontar = useRef(datos)
useEffect(() => {
  if (!datosAlMontar.current) router.replace('/crear-receta')
}, [router])   // no depende de datos — nunca re-dispara al limpiar
