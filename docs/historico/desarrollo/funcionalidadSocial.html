Arquitectura — problema de sincronización SSR ↔ Client

La vista de detalle de receta (/recetas/[id]) es un Server Component que llama al BE en el servidor con getServerSession y pasa los datos como props al Client Component DetalleRecetaCliente. Esto significa que TanStack Query no gestiona el estado de detalle — los datos viven como props de React, no en caché del cliente.

Por qué invalidateQueries no era suficiente

Al hacer queryClient.invalidateQueries(["recetas", "detalle", id]) desde un hook de mutación, no había ninguna query con esa clave en caché (la página se renderizó en servidor), por lo que la invalidación no tenía efecto visible. Los contadores de like y comentarios en la vista detalle quedaban desactualizados hasta recargar con F5.

Solución elegida: router.refresh()

Usuario hace like / comenta / guarda / sigue
→
Optimistic update local (UI instantánea)
→
mutate() al BE
→
onSuccess: router.refresh()
→
Next.js re-corre el Server Component
→
useEffect sincroniza props → estado local

router.refresh() no es una recarga de página completa (no hay flash); es una llamada silenciosa que re-ejecuta los Server Components de la ruta actual y actualiza las props de todos los Client Components suscritos, sin perder el estado no-relacionado (scroll, inputs abiertos, etc.).

Por qué useEffect es necesario

Los Client Components de React no actualizan automáticamente su estado local cuando cambian las props del padre (comportamiento estándar de React). Se añade un useEffect con las props como dependencias para sincronizar el estado local (liked, likes, siguiendo) cuando el Server Component devuelve datos frescos tras el refresh().

// cabeceraReceta.tsx
useEffect(() => {
  setLiked(receta.liked)
  setLikes(receta.likes)
  setSiguiendo(receta.sigueAlAutor)
}, [receta.liked, receta.likes, receta.sigueAlAutor])

Backend — endpoints sociales

EndpointAuthLógica
POST /api/recetas/:id/like Requerida Toggle: si el userId ya está en el array likes[] del modelo Receta lo elimina ($pull), si no lo añade ($addToSet). Devuelve { liked, totalLikes }.
POST /api/recetas/:id/guardar Requerida Toggle en el modelo Usuario: añade o elimina el recetaId del array recetasGuardadas[]. Devuelve { guardado }.
POST /api/recetas/:id/comentarios Requerida Crea un subdocumento Comentario con autorId, texto y fecha. Lo inserta en comentarios[] de la Receta. Devuelve el comentario creado.
POST /api/usuarios/:id/seguir Requerida Toggle en ambos modelos: añade/elimina el seguidor del array seguidores[] del usuario objetivo y actualiza siguiendo[] del usuario autenticado. Devuelve { siguiendo }.

Middleware de autenticación

Todos los endpoints sociales usan requerirAuth (extrae y valida el JWT del header Authorization: Bearer <token>). El endpoint GET /api/recetas y GET /api/recetas/:id usan optionalAuth para devolver campos personalizados (liked, guardado, sigueAlAutor) cuando hay sesión, o sus valores por defecto (false) cuando no la hay.

Frontend — hooks y componentes

useRecetasFeed.ts — cambios para FEED-001

Dos cambios en la query key y staleTime para que el feed siempre muestre datos frescos y autenticados:

queryKey: ["recetas", "feed", q ?? "", filtrosAvanzados, pagina, excluirPropio, !!token],
staleTime: 0,
  • !!token en la key: cuando la sesión carga (token pasa de undefined a string), la key cambia y TanStack Query hace un nuevo fetch con el header de autenticación. Sin esto, el feed inicial se servía sin auth y los campos guardado y liked eran siempre false.
  • staleTime: 0: el feed siempre se refetch al volver a la vista (mount), garantizando que los cambios hechos en la vista de detalle se reflejen al volver al feed.

tarjetaPost.tsx — simplificación para FEED-001 / LIKE-001

Los likes y comentarios en la tarjeta del feed son solo informativos (no interactivos). Se eliminó toda la lógica de useToggleLike del componente. El único botón interactivo que queda es el de guardado (bookmark).

Por qué: tener dos superficies de interacción para el like (feed + detalle) con estado SSR en el detalle y estado de cliente en el feed creaba desincronización difícil de gestionar. La decisión de simplificar el feed a display-only elimina el problema de raíz y sigue siendo UX válido (Instagram también muestra el conteo en el feed sin permitir like directo en algunas vistas).

// Solo display — sin onClick, sin estado local de like
<div className="flex items-center gap-1.5">
  <Heart className="h-5 w-5 text-muted-foreground" strokeWidth={1.8} />
  <span className="text-sm text-muted-foreground">{post.likes}</span>
</div>

useToggleLike.ts — simplificado

Versión final sin onMutate (el optimistic update lo gestiona el estado local de cabeceraReceta.tsx). En onSuccess invalida las queries del feed para que al volver los contadores sean correctos.

onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ["recetas", "feed"] })
  queryClient.invalidateQueries({ queryKey: ["recetas", "detalle", recetaId] })
},

useToggleGuardado.ts — patrón onMutate

El guardado sí mantiene onMutate con snapshot y rollback porque el bookmark sí es interactivo en el feed. El flujo completo: snapshot → update optimista en caché → en onError rollback → en onSettled invalidate.

useAgregarComentario.ts — simplificado

Igual que useToggleLike: el optimistic update lo gestiona el estado local de comentariosReceta.tsx (añade el comentario a listaLocal antes de que el servidor responda). El hook solo invalida queries en onSuccess.

comentariosReceta.tsx — optimistic update local

const optimista: Comentario = {
  autorNombre: session?.user?.name ?? 'Tú',
  avatarUrl: session?.user?.image ?? null,
  texto: textoTrimmed,
  fecha: new Date().toISOString(),
}
setListaLocal((prev) => [optimista, ...prev])
setTexto('')

enviar(textoTrimmed, {
  onSuccess: () => router.refresh(),
  onError: () => {
    setListaLocal((prev) => prev.filter((c) => c !== optimista))
    setTexto(textoTrimmed)   // restaura el texto para que el usuario no lo pierda
  },
})

detalleRecetaCliente.tsx

Añadido useRouter y router.refresh() en el onSuccess de mutarGuardado. Antes solo hacía el optimistic update local sin resincronizar con el servidor.

cabeceraReceta.tsx — botón Compartir (DET-003)

Añadido estado urlCopiada y función handleCompartir. En móvil abre el share sheet nativo del SO; en escritorio copia la URL al portapapeles y muestra feedback visual durante 2 segundos.

const [urlCopiada, setUrlCopiada] = useState(false)

async function handleCompartir() {
  const url = window.location.href
  if (navigator.share) {
    try { await navigator.share({ title: receta.receta.titulo, url }) } catch {}
  } else {
    try {
      await navigator.clipboard.writeText(url)
      setUrlCopiada(true)
      setTimeout(() => setUrlCopiada(false), 2000)
    } catch {}
  }
}

El botón cambia de icono (Share2 → Check) y de label ("Compartir" → "¡Copiado!") con text-brand mientras urlCopiada === true. No se necesita hook ni service porque no es una llamada HTTP — es una API del navegador, equivalente a router.push() en términos de capa arquitectónica.

page.tsx (/recetas/[id]) — export dynamic

Añadido export const dynamic = 'force-dynamic'. Sin esto, Next.js cachea el render del Server Component en el router cache del cliente. Al navegar de vuelta a la misma receta, Next.js servía el render antiguo (con sigueAlAutor: false) en lugar de hacer un nuevo fetch. Con force-dynamic, cada visita a la ruta re-ejecuta el Server Component en el servidor.

export const dynamic = 'force-dynamic'

Sincronización feed ↔ detalle

Flujo completo de un like

1. Click en ❤️ en cabeceraReceta
→
setLiked(!liked), setLikes(±1) — UI instantánea
2. mutarLike() — POST /api/recetas/:id/like
3a. onSuccess → router.refresh()
→
Server Component re-fetch → useEffect sincroniza estado
3b. onSuccess → invalidateQueries(["recetas","feed"])
→
Feed marca sus queries stale → refetch al volver
4. onError → rollback setLiked, setLikes

Flujo completo de un comentario

1. Click en Publicar
→
setListaLocal([comentario_optimista, ...prev]) — aparece inmediatamente
2. enviar(texto) — POST /api/recetas/:id/comentarios
3a. onSuccess → router.refresh() → lista real desde BD
3b. onError → eliminar optimista de lista, restaurar texto
Limitación conocida: si el usuario navega muy rápido de vuelta al feed antes de que router.refresh() complete, el feed puede mostrar el valor pre-mutación durante un instante. Esto es aceptable para un TFG y se resolvería en producción con WebSockets o un estado global Zustand compartido entre feed y detalle.
🤔

Decisiones de diseño

DecisiónAlternativa descartadaMotivo
router.refresh() como mecanismo de sync invalidateQueries en el detalle El detalle no tiene queries TanStack — es SSR puro. invalidateQueries no tenía efecto porque no había nada en caché que invalidar.
Likes/comentarios display-only en el feed Interactivos en feed con onMutate en caché Mantener dos superficies de interacción (feed + detalle) sincronizadas con SSR es complejo y propenso a bugs. Display-only en feed elimina el problema sin sacrificar UX relevante.
export const dynamic = 'force-dynamic' Revalidación con revalidatePath revalidatePath requiere llamarse desde Server Actions o Route Handlers. Como las mutaciones se hacen desde Client Components vía hooks, force-dynamic es la solución más directa.
!!token en la query key del feed Forzar refetch manual al detectar sesión TanStack Query refetch automáticamente cuando la key cambia. Al incluir !!token, el paso de no-autenticado a autenticado (booleano cambia de false a true) dispara el refetch con las credenciales correctas sin código adicional.
Optimistic update local en el componente Optimistic update vía onMutate en el hook El detalle es SSR, no hay query en caché para actualizar con setQueryData. El estado local del componente es la única capa de estado disponible; el hook solo invalida el feed.

DET-004 — Paginación de comentarios con infinite scroll ✅ Sprint 5

Problema original

Todos los comentarios de una receta llegaban por SSR embebidos en RecetaDetalle.listaComentarios[]. El Sheet de "Ver todos" simplemente mostraba ese array completo sin paginación. Para recetas con muchos comentarios esto generaba respuestas SSR grandes innecesariamente.

Endpoint nuevo — BE

GET /api/recetas/:id/comentarios?pagina=1&limite=8

Respuesta:
{
  comentarios: [{ autorNombre, avatarUrl, texto, fecha }],
  total: number,
  hayMas: boolean
}

Auth: optionalAuth (comentarios son públicos)
Orden: más recientes primero (.slice().reverse() del subdocumento)

Capas BE modificadas

ArchivoCambio
recetaRepository.tsAñadido findComentarios(id, pagina, limite) — slice del array embebido en Mongoose, reversed, paginado en memoria
recetasService.tsAñadido obtenerComentarios(id, pagina, limite) — delegación directa al repository
recetasController.tsAñadido obtenerComentarios() — parsea query params con defaults (pagina=1, limite=8, máx 20)
recetas.routes.tsAñadida ruta GET /:id/comentarios con optionalAuth

Hook FE — useComentarios.ts

// frontend/src/features/recetas/hooks/useComentarios.ts
useInfiniteQuery({
  queryKey: ['comentarios', recetaId],
  queryFn: ({ pageParam }) => recetasService.obtenerComentarios(recetaId, pageParam),
  getNextPageParam: (lastPage, allPages) =>
    lastPage.hayMas ? allPages.length + 1 : undefined,
  initialPageParam: 1,
  staleTime: 0,
})

También exporta useInvalidarComentarios(recetaId) — wrapper de queryClient.invalidateQueries que se llama en onSuccess al añadir un comentario.

Componente — comentariosReceta.tsx

ZonaDatos usadosPor qué
Preview (fuera del Sheet)[...nuevos, ...comentariosSSR].slice(0,3)Renderizado instantáneo desde SSR, sin esperar la query
Sheet interiorSolo data?.pages.flatMap(p => p.comentarios)Evita duplicados: el array nuevos queda fuera para que al invalidar la query no aparezca dos veces
Nuevo comentarioPrepend a nuevos (optimista) → invalidar() en onSuccessFeedback inmediato + refresco de la query para el Sheet

Infinite scroll — IntersectionObserver

Un div sentinel al final de la lista del Sheet es observado con IntersectionObserver (threshold: 0.1). Cuando entra en viewport y hay más páginas disponibles, se llama fetchNextPage() automáticamente. Mientras carga aparecen 2 skeletons con la anatomía real del comentario. Cuando no hay más páginas se muestra "Has visto todos los comentarios".

usuario scrollea al final → sentinel entra en viewport → fetchNextPage() → GET /comentarios?pagina=N → skeletons → nuevos items

UX / Affordance — Sheet rediseñado

  • Handle visual (pastilla gris) en la parte superior — señal táctil estándar de bottom sheet (iOS/Android)
  • Título centrado con total de comentarios — patrón Instagram
  • Input de comentario dentro del Sheet — el usuario no necesita cerrarlo para comentar
  • Skeletons con anatomía real (círculo avatar + líneas de texto) en lugar de bloques genéricos
  • CTA secundario bajo la preview: "Ver los N comentarios" (texto gris) — refuerza que hay más sin interrumpir el flujo

Decisión: paginación en memoria vs query MongoDB

Los comentarios se almacenan como subdocumento embebido en el documento Receta (listaComentarios[]). MongoDB no tiene slice nativo eficiente en subdocumentos con paginación + orden inverso, y el volumen esperado (decenas, raramente centenas) no justifica una colección separada. Se opta por cargar el documento completo y paginar en Node con .slice().reverse(). Si en el futuro los comentarios superan los 500 por receta, se migrará a colección propia con índice de fecha.
