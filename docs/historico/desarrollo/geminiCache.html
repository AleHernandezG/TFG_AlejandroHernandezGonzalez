Cachés implementados

1 — Contexto de usuario (mayor impacto)

Tipo: Map<usuarioId, {contexto, expira}> TTL: 5 minutos Máximo: 100 entradas Limpieza: automática al superar el límite

Evita las 2 queries a MongoDB en cada mensaje del chat. El contexto (preferencias, alergias, despensa) no cambia durante una conversación normal. Si el usuario actualiza su despensa y vuelve al chat, el contexto se refresca automáticamente al expirar el TTL.

2 — Singleton del cliente Gemini

Tipo: variable de módulo _genAI TTL: sin expiración (vida del proceso)

La instancia GoogleGenerativeAI se crea una sola vez y se reutiliza en todas las funciones del módulo. El model con systemInstruction no se puede cachear (varía según el contexto de cada usuario), pero el cliente base sí.

3 — Recetas generadas desde texto

Tipo: Map<descripcionNormalizada, {resultado, expira}> TTL: 2 minutos

Protege ante doble-submit. La clave es la descripción normalizada (trim().toLowerCase().replace(/\s+/g, ' ')). TTL corto de 2 minutos: suficiente para absorber el tiempo entre el primer click y un posible segundo intento, sin retener resultados obsoletos.

Flujos con caché

Chat — mensaje del usuario

responderChat(mensajes, usuarioId) → cacheContexto.get(usuarioId) → HIT → contexto en memoria / MISS → 2 queries MongoDB → set cache → Gemini API

Crear receta con IA

generarRecetaDesdeTexto(desc) → cacheRecetaGenerada.get(clave) → HIT → receta en memoria (doble-submit) / MISS → Gemini API → set cache 2 min

Escanear ticket (sin caché)

escanearTicket(imagenBase64) → obtenerCliente() singleton → Gemini Vision API

Las imágenes de ticket son siempre únicas, no tiene sentido cachearlas.

Código clave

Singleton del cliente

let _genAI: GoogleGenerativeAI | null = null;

function obtenerCliente(): GoogleGenerativeAI {
  const apiKey = process.env.GEMINI_API_KEY;
  if (!apiKey) throw Object.assign(new Error("GEMINI_API_KEY no configurada"), { status: 503 });
  if (!_genAI) _genAI = new GoogleGenerativeAI(apiKey);
  return _genAI;
}

Caché de contexto con TTL y límite

const cacheContexto = new Map<string, EntradaContexto>();
const TTL_CONTEXTO_MS = 5 * 60 * 1000;
const MAX_ENTRADAS_CONTEXTO = 100;

async function obtenerContextoUsuario(usuarioId: string): Promise<string> {
  const ahora = Date.now();
  const entrada = cacheContexto.get(usuarioId);

  if (entrada && entrada.expira > ahora) return entrada.contexto; // cache hit

  // cache miss → queries a MongoDB
  const usuario = await usuarioRepository.buscarPerfilPorId(usuarioId);
  const despensaDoc = usuario
    ? await Usuario.findById(usuarioId).select("despensa").lean().exec()
    : null;
  // ... construir contexto ...

  if (cacheContexto.size >= MAX_ENTRADAS_CONTEXTO) limpiarContextosExpirados();
  cacheContexto.set(usuarioId, { contexto, expira: ahora + TTL_CONTEXTO_MS });
  return contexto;
}

Invalidación manual (para uso futuro)

// Exportada para que otros módulos puedan forzar refresco
// (ej: si despensaRepository llama a esto tras una mutación)
export function invalidarContextoUsuario(usuarioId: string): void {
  cacheContexto.delete(usuarioId);
}

Decisiones de diseño

Sin Redis, sin infraestructura adicional

El caché vive en la memoria del proceso Node. Para el TFG es suficiente: un solo proceso en Render, el caché se comparte entre todas las requests de ese proceso. Si escalara a múltiples instancias se necesitaría Redis, pero ese escenario está fuera del alcance.

TTL 5 min para contexto, 2 min para recetas

5 minutos es suficiente para una conversación de chat fluida sin recargar el contexto entre cada mensaje. Si el usuario actualiza su despensa y vuelve, el contexto se refresca solo al expirar. 2 minutos para recetas generadas es suficiente para absorber doble-submits sin retener resultados obsoletos.

Limpieza pasiva por expiración

No hay un intervalo periódico de limpieza. La limpieza ocurre solo cuando se supera MAX_ENTRADAS_CONTEXTO. Para 100 usuarios activos simultáneos (máximo realista en un TFG) el Map nunca crece demasiado.

El model con systemInstruction no se cachea

El systemInstruction incluye el contexto personalizado de cada usuario. Como el contexto es diferente por usuario y cambia con el tiempo, crear un modelo cacheado por userId añadiría complejidad sin beneficio claro frente a cachear solo el contexto string.
