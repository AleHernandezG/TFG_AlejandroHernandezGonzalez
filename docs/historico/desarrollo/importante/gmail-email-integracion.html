Fecha: 2026-04-23  ·  Sprint 3 BE  ·  Operativo en producción

1. Resumen de cambios

Se integró Nodemailer con Gmail SMTP para enviar emails de verificación de cuenta y recuperación de contraseña. Se eliminaron todas las rutas y código temporal de desarrollo que existían mientras el email no estaba operativo.

2. Flujo — Verificación de cuenta

Usuario se registra
→
POST /api/auth/registro
→
Se crea usuario en MongoDB
→
Se crea token tipo:verificacion (24h TTL)
→
enviarEmailVerificacion()
→
Email llega con enlace /verificar-email?token=xxx
→
Usuario hace clic
→
POST /api/auth/verificar-email
→
cuentaVerificada=true
→
Puede iniciar sesión

Si Gmail SMTP falla, el error se loguea pero no se hace throw: el usuario ya está creado en DB y el token existe en MongoDB. Puede solicitar un reenvío desde /verificar-email/pendiente usando el botón "Reenviar correo", que llama a POST /api/auth/verificar-email/reenviar — reutiliza enviarEmailVerificacion() tras invalidar el token anterior.

3. Flujo — Recuperación de contraseña

Usuario solicita recuperación
→
POST /api/auth/recuperar-contrasena
→
Se crea token tipo:recuperacion (1h TTL)
→
enviarEmailRecuperacion()
→
Email con enlace /nueva-contrasena?token=xxx
→
Usuario establece nueva contraseña
→
POST /api/auth/nueva-contrasena
→
Token invalidado en DB

La respuesta de /recuperar-contrasena es siempre genérica ("Si existe una cuenta con ese correo…") para no revelar si el correo está registrado.

5. Configuración Gmail SMTP — paso a paso

  1. Abre tu cuenta de Gmail y ve a Gestionar tu cuenta de Google.
  2. Navega a Seguridad y activa Verificación en 2 pasos si no está activa.
  3. Con la verificación en 2 pasos activa, aparece la opción Contraseñas de aplicación en la misma sección.
  4. Crea una nueva contraseña de aplicación para la categoría "Correo".
  5. Copia los 16 caracteres generados (con o sin espacios, ambos funcionan).
  6. En backend/.env, añade: 
    GMAIL_USER=tucuenta@gmail.com
GMAIL_APP_PASSWORD=xxxx xxxx xxxx xxxx
  7. Reinicia el backend.

6. Límites Gmail y consideraciones para producción

AspectoDetalle
Límite diario~500 emails/día por cuenta Gmail. Suficiente para un TFG.
EntregabilidadGmail tiene buena reputación de dominio. Los emails llegan a bandeja de entrada en la mayoría de clientes.
Sin dominio propioFunciona con cuenta @gmail.com. No requiere DNS, SPF, DKIM propios.
Para producción realSi el volumen crece, migrar a Resend / SendGrid con dominio verificado para mejor entregabilidad y sin límites.
Cuenta dedicadaRecomendable usar una cuenta Gmail separada solo para Cookr en producción (noreply.cookr@gmail.com).

7. Notas técnicas

  • El envío de email es best-effort: si Gmail falla, el usuario ya está creado en DB y puede usar el botón "Reenviar correo" de /verificar-email/pendiente, que llama a POST /api/auth/verificar-email/reenviar.
  • Las plantillas usan inline CSS — compatibles con Gmail, Outlook, Apple Mail. No soportan CSS externo ni variables CSS.
  • El color #c47c1a del botón CTA es una aproximación al --brand de la app en oklch (los clientes de email no soportan oklch).

8. Capas — dónde vive la lógica

authController.ts          ← recibe la request HTTP
  └── authService.ts         ← lógica de negocio: crea usuario/token, llama a lib/email
        └── lib/email.ts     ← infraestructura: transporter Nodemailer + plantillas HTML

El controller nunca llama directamente a Gmail SMTP. Sigue el patrón de capas del proyecto: controller → service → lib.
