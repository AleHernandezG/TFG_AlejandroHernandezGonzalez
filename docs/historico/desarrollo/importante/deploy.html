Gemini en producción — Proxy Cloudflare

El problema

Las llamadas a Gemini funcionaban en local pero en Render devolvían 503, con un 403 de Google por debajo. Aparecieron dos errores distintos, que no son lo mismo:

Error de GoogleQué significa
403 · unregistered callers / callers without established identityLa clave llegaba vacía a Google. Pasa cuando la variable tiene espacios o saltos de línea, o no se inyecta bien en el proceso.
403 HTML · "Your client does not have permission to get URL ... from this server"Google bloquea la IP desde la que se llama. Lo sirve el frontend de Google (GFE), no la API.

Diagnóstico

1
La misma clave funciona desde local

Desde una IP residencial la clave responde 200 con cualquier modelo. Eso descarta que el fallo sea la clave, el código o el modelo.

2
Desde Render falla siempre

El fallo es consistente en cada request, no intermitente. Apunta a un bloqueo por origen de red, no a reputación de IP que va y viene.

3
Restricciones de la clave en "Ninguna"

Cloud Console → Credenciales → clave TFG: sin restricción de IP ni de referrer. Por tanto no es una restricción de la clave.

4
Conclusión: bloqueo de IP del nivel gratuito

El tier gratuito de Gemini corta las IPs de datacenter (las de Render) como protección anti-abuso. Por eso funciona desde casa y no desde el servidor.

Migración del SDK

Investigando el 403 se cambió el SDK, que además ya estaba deprecado.

AntesAhora
@google/generative-ai 0.24.1 (deprecado)@google/genai 2.10.0
new GoogleGenerativeAI(key)new GoogleGenAI({ apiKey })
getGenerativeModel() + model.generateContent()models.generateContent({ model, contents, config })
model.startChat() + chat.sendMessage(x)chats.create() + chat.sendMessage({ message: x })

Node ≥ 20: @google/genai lo exige, así que se añadió "engines": { "node": ">=20.0.0" } en backend/package.json para que Render no arranque con una versión vieja. El SDK nuevo manda la clave en la cabecera x-goog-api-key y recorta espacios, más tolerante a variables sucias que el anterior.

Cómo funciona el proxy

El Worker de Cloudflare reenvía las peticiones a Google desde una IP con buena reputación, que Gemini sí acepta.

1
El backend apunta el SDK al Worker

Si existe GEMINI_BASE_URL, obtenerCliente() pasa ese baseUrl al SDK. En local, sin esa variable, las llamadas van directas (desde el equipo de desarrollo funcionan sin proxy).

2
El Worker reenvía tal cual

Copia método, ruta, query, body y cabeceras (incluida x-goog-api-key con la clave). No toca el contenido, solo cambia la IP de salida.

3
Puerta de token

El Worker exige la cabecera x-proxy-token igual a su secreto PROXY_TOKEN. Sin eso sería un proxy abierto. El backend la manda vía GEMINI_PROXY_TOKEN. Si no coinciden, el Worker responde 403.

Worker desplegado:

https://gemini-proxy.alejes.workers.dev

Código en gemini-proxy/ del repo. El núcleo:

export default {
  async fetch(request, env) {
    if (env.PROXY_TOKEN && request.headers.get("x-proxy-token") !== env.PROXY_TOKEN) {
      return new Response("Forbidden: invalid proxy token", { status: 403 });
    }
    const url = new URL(request.url);
    const target = "https://generativelanguage.googleapis.com" + url.pathname + url.search;
    const headers = new Headers(request.headers);
    // se quitan host, x-proxy-token y las cabeceras cf-* / x-forwarded-*
    const body = ["GET", "HEAD"].includes(request.method) ? undefined : await request.arrayBuffer();
    return fetch(target, { method: request.method, headers, body });
  },
};

GitHub Actions — Workflow

Archivo: .github/workflows/ci-cd.yml

name: CI / CD — Cookr

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  ci-frontend:               # Lint + tsc --noEmit
    runs-on: ubuntu-latest
    working-directory: frontend

  ci-backend:                # tsc --noEmit
    runs-on: ubuntu-latest
    working-directory: backend

  deploy:                    # Solo en push a main
    needs: [ci-frontend, ci-backend]
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      # Vercel se gestiona solo (integración nativa GitHub)
      - name: Deploy backend → Render (Deploy Hook)
        run: |
          STATUS=$(curl -s -o /dev/null -w "%{http_code}" "${{ secrets.RENDER_DEPLOY_HOOK_URL }}")
          echo "Render deploy hook HTTP status: $STATUS"
          # Render responde 202 Accepted (deploy asíncrono)
          [ "$STATUS" = "200" ] || [ "$STATUS" = "201" ] || [ "$STATUS" = "202" ] || exit 1

Actions actualizadas a actions/checkout@v5 y actions/setup-node@v5, y Node del CI a 22. Node 20 quedó deprecado como runtime de las actions en los runners, y @google/genai pide Node ≥ 20.

Branch protection en main

✓
Require a pull request before merging

No se puede hacer push directo a main. Todo debe entrar por PR.

✓
Require status checks to pass

Checks requeridos: Lint & typecheck — Frontend y Typecheck — Backend. La PR no se puede mergear si alguno falla.

✓
Do not allow bypassing

Ni el administrador puede saltarse las reglas.

Workflow diario de desarrollo

1
Trabajar en develop

Todos los cambios van a develop. Nunca commitear directo a main.

2
Push a develop

GitHub Actions corre CI automáticamente. Si falla lint o typecheck, hay que arreglarlo antes de continuar.

3
PR develop → main al terminar una feature o sprint

GitHub exige que CI pase para poder mergear. Revisar los checks en la PR.

4
Merge → deploy automático

Vercel despliega el FE. GitHub Actions dispara el Deploy Hook de Render para el BE. En ~3 min la app está actualizada en producción.

5
Antes de demos

Ejecutar bash scripts/keep-alive.sh para evitar el cold start de Render. URL configurada: https://tfg-alejandrohernandezgonzalez.onrender.com.
