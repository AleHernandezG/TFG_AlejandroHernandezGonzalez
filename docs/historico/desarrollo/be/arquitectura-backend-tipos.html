Separación de interfaces de dominio y schemas Mongoose

Refactorización de la capa de modelos para desacoplar el contrato de dominio de los detalles de persistencia en MongoDB — mejora de escalabilidad y mantenibilidad.

⚠ El problema: responsabilidades mezcladas

Antes de esta refactorización, cada archivo *.model.ts mezclaba dos responsabilidades distintas en el mismo fichero:

✕ Antes — usuario.model.ts
// ① INTERFAZ DE DOMINIO
// (contrato que usan repositories, services...)
export interface IUsuario extends Document {
  nombre: string
  correo: string
  rol: "usuario" | "admin"
  // ...
}

// ② SCHEMA MONGOOSE
// (detalles de persistencia MongoDB)
const usuarioSchema = new Schema<IUsuario>({
  nombre: { type: String, trim: true, ... }
  correo: { unique: true, lowercase: true }
  contrasena: { select: false } // ← detalle Mongoose
})

export const Usuario = mongoose.model(...)
✓ Ahora — separado en dos capas
// types/usuario.ts
// Solo el contrato de dominio
export interface IUsuario {
  nombre: string
  correo: string
  rol: "usuario" | "admin"
  // ...
}

// models/usuarioMongo.ts
// Solo el schema de persistencia
export interface IUsuarioDoc
  extends IUsuario, Document {}

const usuarioSchema = new Schema<IUsuarioDoc>({...})
export const Usuario = mongoose.model(...)
¿Por qué es un problema mezclarlos?

Si la interfaz vive dentro del archivo del schema, cualquier cambio en cómo MongoDB persiste los datos (añadir un índice, cambiar select: false, renombrar una opción de Mongoose) obliga a repasar todos los archivos que importan esa interfaz — aunque solo les importe el tipo, no el schema.

📁 Estructura de archivos resultante

backend/src/
  ├── types/                  ← NUEVA CAPA
  │   ├── usuario.ts         IUsuario — contrato de dominio puro
  │   └── token.ts           IToken — contrato de dominio puro
  ├── models/
  │   ├── usuarioMongo.ts    IUsuarioDoc + schema Mongoose
  │   └── tokenMongo.ts      ITokenDoc + schema Mongoose + TTL index
  ├── repositories/
  │   ├── usuarioRepository.ts importa IUsuario de types/ + Usuario de models/
  │   └── tokenRepository.ts   importa IToken de types/ + Token de models/
  └── services/ controllers/ routes/ ...
La nomenclatura Xxxxxuario.ts → nombreMongo.ts hace explícito qué BD está vinculada: si mañana aparece un usuarioPostgres.ts o usuarioRedis.ts, el equipo sabe inmediatamente qué motor usa cada archivo.

Regla clave: Los services/ y controllers/ nunca importan desde models/ directamente. Solo hablan con repositories/. Los repositories/ son los únicos que conocen tanto las interfaces (types/) como los schemas Mongoose (models/).

⚙ Cómo se implementó

El patrón aplicado en cada entidad es siempre el mismo:

① Interface de dominio — types/usuario.ts

// Sin ningún import de Mongoose — solo TypeScript puro
export interface IUsuario {
  nombre: string
  correo: string
  contrasena?: string
  foto?: string
  rol: "usuario" | "admin"
  cuentaVerificada: boolean
  proveedor: "local" | "google"
  googleId?: string
  alergias: string[]
  preferencias: string[]
  fechaRegistro: Date
}

② Schema y modelo Mongoose — models/usuarioMongo.ts

import { IUsuario } from "../types/usuario"
import mongoose, { Schema, Document } from "mongoose"

// IUsuarioDoc = dominio + métodos Document (._id, .save, etc.)
export interface IUsuarioDoc extends IUsuario, Document {}

// Solo aquí viven los detalles de MongoDB
const usuarioSchema = new Schema<IUsuarioDoc>({
  contrasena: { type: String, select: false }, // ← detalle Mongoose
  correo:     { unique: true, lowercase: true },  // ← detalle Mongoose
  // ...
})
export const Usuario = mongoose.model<IUsuarioDoc>("Usuario", usuarioSchema)
export type { IUsuario } // re-export de conveniencia

③ Repository — repositories/usuarioRepository.ts

import { IUsuario }              from "../types/usuario"     // contrato
import { IUsuarioDoc, Usuario } from "../models/usuarioMongo" // Mongoose

export const usuarioRepository = {
  buscarPorCorreo: (correo: string): Promise<IUsuarioDoc | null> =>
    Usuario.findOne({ correo }),
  // los métodos devuelven IUsuarioDoc para que _id esté disponible
  // en authService sin importar nada de Mongoose desde el service
}

★ Beneficios concretos

⟳ Cambio sin efecto cascada
Añadir un índice, cambiar una opción de Mongoose, o renombrar un campo en el schema solo toca models/. Los types/ (lo que ve el resto del código) permanecen intactos.
⬡ Cambio de base de datos
Si en el futuro se usa PostgreSQL, Redis o cualquier otro motor, solo cambian models/ (ORM/cliente) y repositories/ (queries). Las interfaces en types/ y toda la lógica en services/ no se tocan.
◈ Legibilidad de imports
Al ver import { IUsuario } from "../types/usuario" en un archivo, sabes de inmediato que solo necesitas el tipo. Al ver from "../models/usuarioMongo" sabes que hay operaciones de BD involucradas.
⊙ Nomenclatura BD-explícita
El sufijo Mongo en los modelos indica qué motor de BD usa ese archivo. Si aparece usuarioPostgres.ts en el futuro, la distinción es inmediata sin abrir el archivo.
⊞ Testing más sencillo
Los tests unitarios de services/ pueden importar IUsuario desde types/ para construir mocks sin depender de Mongoose ni de una conexión a MongoDB.
⊛ Sin cambios funcionales
El schema Mongoose es idéntico al anterior. Ningún endpoint, controller ni servicio cambió su comportamiento. La refactorización es 100% estructural.

→ Escenarios de cambio futuro

Escenario A — Añadir un campo al modelo (ej: "bio")
1 Añadir bio?: string a types/usuario.ts
2 Añadir el campo al schema en models/usuarioMongo.ts
3 TypeScript señala automáticamente dónde usarlo si es requerido

repositories/, services/ y controllers/ no necesitan cambio si el campo es opcional.

Escenario B — Cambiar el motor de BD (MongoDB → PostgreSQL)
1 Crear models/usuarioPostgres.ts con el ORM de Postgres (ej: Prisma/TypeORM)
2 Reescribir repositories/usuarioRepository.ts con las queries de Postgres
3 types/usuario.ts, services/ y controllers/ — sin tocar
Escenario C — Añadir caché Redis sobre el repository
1 Crear models/usuarioRedis.ts con el cliente Redis
2 Actualizar el repository para consultar Redis antes que MongoDB
3 El resto del código sigue usando la misma interfaz IUsuario

≡ Nomenclatura adoptada

Capa Convención Ejemplo Por qué
Types BE nombre.ts usuario.ts NUEVO Al estar en types/ ya está claro que son interfaces. Sin sufijo redundante.
Models BE nombreMongo.ts usuarioMongo.ts NUEVO El sufijo indica qué BD usa. Si hay más motores, la distinción es inmediata.
Types FE nombre.types.ts receta.types.ts En FE los types conviven con datos mock, hooks, etc. El sufijo ayuda a distinguirlos.
Repositories nombreRepository.ts usuarioRepository.ts Sin cambio — la convención ya era correcta.
