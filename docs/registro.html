1. ¿Qué es la página de registro y para qué sirve?

La página de registro es la puerta de entrada a la aplicación. Su misión es permitir que un visitante nuevo cree una cuenta para poder usar Gastronómica. Está en la ruta /registro y el usuario llega aquí normalmente pulsando el botón "Crear cuenta" de la landing page.

La página ofrece dos formas de registrarse, pensadas para minimizar la fricción (cuanto menos pasos, más usuarios completan el registro):

MétodoCómo funcionaEstado actual
Google OAuth El usuario pulsa un botón y Google gestiona todo el proceso de identidad. No hay que escribir nada: Google confirma quién es la persona y devuelve sus datos al app. Funcional
Email + contraseña El usuario rellena un formulario con nombre, correo y contraseña. Los datos se validan localmente antes de enviarse. El envío es un mock hasta que el backend esté listo en Fase 4. Validación lista — envío mock
¿Qué significa "mock"? En desarrollo, cuando todavía no existe un servidor real al que enviar datos, se simula una respuesta. El formulario valida correctamente todos los campos, pero en lugar de llamar a una API real, espera 1 segundo (simula latencia de red) y muestra la pantalla de éxito. Cuando el backend esté implementado en Fase 4, solo hay que sustituir esa línea por la llamada real.

Visualmente la página usa un layout split-screen (referentes: Linear, Spotify, Netflix): en pantallas grandes (≥ lg) la pantalla se divide en dos paneles horizontales. En móvil la imagen desaparece y el formulario ocupa toda la pantalla.

2. Conceptos clave para entender el código

El registro introduce herramientas que no aparecían en la landing page. Antes de leer los componentes, estos son los conceptos que necesitas tener claros:

Formularios controlados vs. no controlados

En React, un formulario "controlado" es aquel en el que cada campo está vinculado a un estado de React — cada tecla que pulsa el usuario actualiza una variable en el componente. Un formulario "no controlado" deja que el DOM gestione los valores internamente y React solo los lee cuando los necesita (por ejemplo, al enviar).

React Hook Form usa el enfoque no controlado por defecto, lo que lo hace muy eficiente: no hay rerenders por cada tecla. Los valores se leen del DOM solo cuando se valida o se envía el formulario. La función register() es la que "registra" cada campo del formulario en React Hook Form sin necesidad de useState. 

// Sin React Hook Form necesitaríamos un useState por cada campo:
const [nombre, setNombre] = useState("");
const [correo, setCorreo] = useState("");
const [contrasena, setContrasena] = useState("");
// ... y manejadores onChange para cada uno. Muy repetitivo.

// Con React Hook Form: registro sin estado extra
<Input {...register("nombre")} />
<Input {...register("correo")} />
<Input {...register("contrasena")} />

Zod — Validación con esquemas tipados

Zod es una librería para definir la forma que deben tener los datos y validarlos. En lugar de escribir funciones de validación a mano ("si el campo está vacío, muestra este error…"), se describe el esquema de datos una sola vez y Zod lo valida automáticamente.

La ventaja principal es que el esquema Zod también genera el tipo TypeScript automáticamente con z.infer<typeof esquema>. Así el tipo y la validación nunca se desincronizarán porque son el mismo objeto. 

// Zod define el esquema UNA vez y da validación + tipo TypeScript
const esquemaRegistro = z.object({
  nombre: z.string().min(2),     // mínimo 2 caracteres
  correo: z.string().email(),   // debe ser un email válido
  contrasena: z.string().min(8),// mínimo 8 caracteres
});

// z.infer extrae el tipo TypeScript del esquema Zod:
type DatosRegistro = z.infer<typeof esquemaRegistro>;
// Equivale a: { nombre: string; correo: string; contrasena: string }

zodResolver — El puente entre Zod y React Hook Form

React Hook Form tiene su propio sistema de validación, pero también permite usar validadores externos. zodResolver es el adaptador que convierte el esquema Zod en algo que React Hook Form puede ejecutar automáticamente al intentar enviar el formulario o al escribir en un campo. Sin él, habría que pasar las reglas de validación manualmente a cada register(). 

const { register, handleSubmit, formState: { errors } } = useForm<DatosRegistro>({
  resolver: zodResolver(esquemaRegistro), // ← aquí se conectan
});
// Ahora React Hook Form ejecutará esquemaRegistro.parse() al validar

handleSubmit — Prevenir el envío sin validación

En HTML nativo, cuando un formulario se envía, el navegador recarga la página. En React eso no queremos que pase. handleSubmit de React Hook Form es una función que: 1) previene el comportamiento del navegador, 2) ejecuta la validación Zod sobre todos los campos, y 3) solo llama a tu función (alEnviar) si todos los campos pasan la validación. Si hay errores, los pone disponibles en el objeto errors. 

<form onSubmit={handleSubmit(alEnviar)}>
  //                   ↑ tu función solo se llama si todos los campos son válidos
  <Input {...register("correo")} />
  {errors.correo && <p>{errors.correo.message}</p>} // ← muestra el error
</form>

NextAuth — Autenticación lista para usar

NextAuth.js es una librería que implementa flujos completos de autenticación sin tener que construirlos desde cero. Gestiona el intercambio de tokens con Google, la creación de sesiones y cookies de forma segura, y las redirecciones de login/logout. En el proyecto lo usamos para el botón "Registrarse con Google": en un solo clic, el usuario va a Google, da permiso, y NextAuth devuelve sus datos al app creando una sesión automáticamente.

OAuth 2.0 — El protocolo de "Continúa con Google"

OAuth 2.0 es un protocolo estándar de la industria que permite que una app (Gastronómica) delegue la autenticación a otro servicio (Google) sin ver la contraseña del usuario. El flujo simplificado es:

  • El usuario pulsa "Registrarse con Google" → el app redirige a accounts.google.com
  • Google muestra su pantalla de selección de cuenta y pide permiso
  • El usuario acepta → Google redirige de vuelta a /api/auth/callback/google con un código
  • NextAuth intercambia ese código por un token y crea la sesión del usuario
  • El usuario llega a la callbackUrl configurada ya autenticado

Server Component vs. Client Component en la página de registro

La ruta /registro usa dos capas: el page.tsx es un Server Component (sin "use client"), lo que permite exportar metadata para SEO sin coste de JavaScript en el navegador. Dentro renderiza FormularioRegistro que sí es un Client Component porque necesita useState y eventos. Next.js sabe distinguirlos automáticamente. 

// page.tsx — Server Component (no lleva "use client")
export const metadata = { title: "Crear cuenta — Gastronómica" }; // ← solo funciona en server
export default function PaginaRegistro() {
  return <FormularioRegistro />; // ← este sí es client, pero puede estar dentro
}

// formularioRegistro.tsx — Client Component
"use client";
import { useState } from "react";
// ... hooks, eventos, etc.

3. Estructura de archivos del feature auth

El registro introduce un nuevo feature en la arquitectura: features/auth/. Siguiendo el mismo patrón feature-based que la landing, todo lo relacionado con autenticación vive en esta carpeta. Además, se añaden dos archivos fuera de features: la configuración de NextAuth en lib/auth.ts y el route handler en app/api/auth/.

frontend/src/ │ ├── app/ │ ├── api/ │ │ └── auth/ │ │ └── [...nextauth]/ ← ruta dinámica que captura todo /api/auth/* │ │ └── route.ts ← route handler GET/POST para NextAuth │ │ │ ├── registro/ │ │ └── page.tsx ← ruta /registro (Server Component) │ │ │ ├── page.tsx ← ruta / (landing — sin cambios) │ └── layout.tsx │ ├── lib/ │ ├── utils.ts ← utilidad cn() de shadcn — NO TOCAR │ └── auth.ts ← opcionesAuth: GoogleProvider + JWT + callbacks │ └── features/ ├── landing/ ← sin cambios │ └── ... └── auth/ ← nuevo feature de autenticación ├── components/ │ ├── botonGoogle.tsx ← botón OAuth con SVG + estado de carga │ ├── divisorOAuth.tsx ← separador "o continúa con correo" │ ├── formularioRegistro.tsx ← formulario completo (componente principal) │ └── index.ts ← barrel export del feature auth └── types/ └── autenticacion.ts ← esquema Zod + tipos TypeScript
¿Por qué auth.ts está en lib/ y no en features/auth/? La configuración de NextAuth (opcionesAuth) la necesitan tanto el route handler (app/api/auth/[...nextauth]/route.ts) como futuros Server Components que quieran leer la sesión con getServerSession(opcionesAuth). Al ser compartida entre la capa de rutas API y la capa de componentes, se coloca en lib/ — la carpeta de utilidades compartidas — en lugar de dentro del feature.
¿Qué es [...nextauth]? Los corchetes y los puntos suspensivos En Next.js App Router, los corchetes en el nombre de una carpeta indican un segmento dinámico. Los tres puntos (...) hacen que sea un catch-all: captura cualquier ruta que empiece por /api/auth/ independientemente de cuántos segmentos tenga. NextAuth necesita esto porque gestiona múltiples endpoints: /api/auth/signin, /api/auth/callback/google, /api/auth/session, /api/auth/signout, etc.

¿Por qué el layout está en page.tsx y no en FormularioRegistro? El fondo, la imagen y el split-screen pertenecen al layout de la página, no al formulario. Si el formulario se reutiliza en un modal o en otro contexto (por ejemplo, un drawer lateral), no debería llevarse el layout con él. Esta separación es la misma que aplican Linear, Vercel y otros productos modernos: el componente de formulario es "tonto" respecto al layout exterior.
¿Por qué un gradiente oscuro en el panel derecho? bg-background (blanco) era indistinguible de la barra del navegador en la parte superior, dando sensación de continuidad indeseada. El gradiente from-stone-950 to-zinc-950 rompe esa continuidad y crea contraste elegante: la Card blanca del formulario "flota" visualmente sobre el fondo oscuro, igual que en la página de inicio de sesión de Netflix o Linear.
Técnica: gradiente lateral para fusión imagen↔panel El div w-32 bg-gradient-to-r from-transparent to-stone-950 se superpone al borde derecho de la imagen y crea un fundido suave hacia el color exacto del panel del formulario. No hay corte brusco. Este patrón lo usan Spotify (hero → sidebar), Linear (onboarding), y Vercel (páginas de autenticación).

lib/auth.ts — La configuración de NextAuth

Este archivo define opcionesAuth, el objeto de configuración central de NextAuth. Se exporta para poder reutilizarlo en el route handler y en getServerSession() desde cualquier Server Component que necesite leer la sesión. 

export const opcionesAuth: NextAuthOptions = {
  providers: [
    GoogleProvider({
      clientId:     process.env.GOOGLE_CLIENT_ID!,     ← de .env.local
      clientSecret: process.env.GOOGLE_CLIENT_SECRET!, ← de .env.local
    }),
    // TODO Fase 4: añadir CredentialsProvider para email/contraseña
  ],

  pages: {
    signIn:  "/login",    ← si hay error, ir a /login en vez de la página de NextAuth
    newUser: "/registro", ← cuando un usuario nuevo se registra, ir aquí
    error:   "/login",    ← errores de auth también van a /login
  },

  session: { strategy: "jwt" }, ← sin base de datos por ahora (Fases 1-3)

  callbacks: {
    async session({ session, token }) {
      // Añade el ID del usuario a la sesión para usarlo en componentes
      // TODO Fase 4: enriquecer con datos del backend (avatar, rol, etc.)
      if (token.sub) (session.user as { id?: string }).id = token.sub;
      return session;
    },
  },
};
¿Qué es strategy: "jwt"? NextAuth puede guardar la sesión de dos formas: en una base de datos (strategy: "database") o en un token JWT firmado en la cookie del navegador (strategy: "jwt"). Sin base de datos, usamos JWT. El token está firmado con NEXTAUTH_SECRET de .env.local — nadie puede falsificarlo sin conocer ese secreto. La desventaja es que no se puede invalidar una sesión activa individualmente (no hay tabla de sesiones). Para un TFG es suficiente.

app/api/auth/[...nextauth]/route.ts — El route handler

Este archivo es la instalación técnica de NextAuth en Next.js App Router. Es el más corto del proyecto (solo 3 líneas de lógica) pero el más importante para que la autenticación funcione. Sin él, los endpoints /api/auth/* no existirían. 

import NextAuth from "next-auth";
import { opcionesAuth } from "@/lib/auth";

const manejador = NextAuth(opcionesAuth);
// NextAuth devuelve una función que puede manejar tanto GET como POST

export { manejador as GET, manejador as POST };

Next.js App Router requiere que cada route handler exporte funciones nombradas (GET, POST, etc.) en lugar de un handler genérico. Al exportar el mismo manejador como GET y POST, NextAuth puede recibir tanto redirecciones GET (cuando Google devuelve al usuario) como peticiones POST (cuando el formulario envía credenciales o cuando el cliente solicita la sesión).

features/auth/types/autenticacion.ts — Tipos y esquema Zod

Este archivo es el contrato de datos del formulario. Define exactamente qué campos tiene el formulario, qué restricciones tiene cada uno y cuáles son los mensajes de error. Al ser un archivo de tipos puro, no importa React ni ninguna librería de UI. 

export const esquemaRegistro = z
  .object({
    nombre: z.string()
      .min(2, "El nombre debe tener al menos 2 caracteres")
      .max(50, "El nombre no puede superar los 50 caracteres")
      .trim(),  ← elimina espacios al inicio y al final automáticamente

    correo: z.string()
      .email("Introduce un correo electrónico válido")
      .trim(),

    contrasena: z.string()
      .min(8, "La contraseña debe tener al menos 8 caracteres")
      .regex(/[A-Za-z]/, "... al menos una letra")    ← regex: una letra cualquiera
      .regex(/[0-9]/,    "... al menos un número"),   ← regex: un dígito

    confirmarContrasena: z.string(),
  })
  .refine(
    (datos) => datos.contrasena === datos.confirmarContrasena,
    {
      message: "Las contraseñas no coinciden",
      path: ["confirmarContrasena"], ← el error aparece en ese campo concreto
    }
  );

export type DatosRegistro = z.infer<typeof esquemaRegistro>;
export type EstadoFormulario = "idle" | "cargando" | "exito" | "error";
¿Qué es .refine()? .refine() permite añadir una validación personalizada que comprueba el objeto completo, no solo un campo. Se usa cuando la validez de un campo depende del valor de otro (como la confirmación de contraseña, que solo puede validarse sabiendo el valor del campo contraseña). Recibe una función que devuelve true si es válido o false si no lo es, y el objeto de configuración con el mensaje y el path del campo donde aparece el error.

features/auth/components/botonGoogle.tsx — El botón OAuth

Componente reutilizable para lanzar el flujo OAuth de Google. Está pensado para usarse tanto en la página de registro como en la de login sin cambiar código: la diferencia solo es el texto, que se pasa como prop textoAccion. 

export function BotonGoogle({ textoAccion = "Continúa con Google", urlRetorno = "/" }) {
  const [cargando, setCargando] = useState(false);

  const manejarClic = async () => {
    setCargando(true);
    await signIn("google", { callbackUrl: urlRetorno });
    // setCargando(false) nunca llega: el navegador ya habrá redirigido
  };

  return (
    <Button type="button" variant="outline" onClick={manejarClic} disabled={cargando}>
      {cargando ? <Loader2 className="animate-spin" /> : /* SVG Google */}
      {textoAccion}
    </Button>
  );
}

El SVG del logo de Google está embebido directamente en el componente (no como imagen externa) para evitar una petición de red adicional y garantizar que siempre se muestre aunque la CDN esté caída. Los colores del SVG (#4285F4, #34A853, #FBBC05, #EA4335) son los colores oficiales de Google y no deben cambiarse por los colores del proyecto para respetar las guías de marca de Google.

features/auth/components/divisorOAuth.tsx — El separador

Componente puramente visual sin lógica. Muestra una línea horizontal con un texto en el centro. Es un Server Component (no tiene "use client") porque no necesita ningún hook ni interactividad. 

<div className="flex items-center gap-3">
  <Separator className="flex-1" />          ← línea izquierda
  <span className="text-xs text-muted-foreground">{texto}</span>
  <Separator className="flex-1" />          ← línea derecha

Cada Separator tiene flex-1, lo que hace que ambas líneas crezcan para ocupar el espacio disponible a ambos lados del texto, independientemente de la longitud del texto. Esto hace que el componente sea flexible con cualquier texto.

¿Por qué autocomplete="new-password" en los campos de contraseña? Esta pista le dice al navegador y al gestor de contraseñas que estos campos son para crear una contraseña nueva, no para rellenar una existente. El navegador puede entonces ofrecer generar una contraseña segura automáticamente, o guardar la nueva contraseña al enviar el formulario. Es una buena práctica de UX y seguridad.

Toggle de visibilidad de contraseña

Cada campo de contraseña tiene un botón type="button" (importante: si fuera type="submit", enviaría el formulario) que alterna el type del input entre "password" y "text". 

// El type del input cambia según el estado:
<Input
  type={mostrarContrasena ? "text" : "password"}
  {...register("contrasena")}
/>

6. El esquema de validación con Zod

El esquema Zod es el corazón de la validación. Merece su propia sección porque tiene varios comportamientos que es importante entender para depurar problemas futuros.

Cómo funciona la cadena de validadores

Zod aplica los validadores en orden, de izquierda a derecha. Si el primero falla, no ejecuta el siguiente. Por eso el orden importa: tiene sentido poner .min(8) antes de .regex(), porque si la contraseña tiene menos de 8 caracteres, el error de longitud es más informativo que el de "falta una letra".

¿Qué pasa si hay múltiples errores en un campo?

Por defecto, Zod para en el primer error de cada campo (abortEarly: true internamente). Solo se muestra un error a la vez por campo. Si se quisieran mostrar todos los errores a la vez, habría que usar .superRefine() en lugar de encadenar .regex(). Para el registro, mostrar uno a uno es mejor UX: el usuario resuelve un problema cada vez.

El .refine() para la confirmación de contraseña

La validación de que las dos contraseñas coinciden no puede hacerse dentro de un campo individual porque necesita leer el valor de otro campo. Por eso va en .refine() al nivel del objeto completo, después de cerrar el .object({}): 

z.object({ ... })  ← define los campos
 .refine(
   (datos) => datos.contrasena === datos.confirmarContrasena,
   {
     message: "Las contraseñas no coinciden",
     path: ["confirmarContrasena"],  ← el error aparece en ese campo específico
   }
 );

El campo path en la configuración de .refine() es crucial: sin él, el error aparecería a nivel del formulario completo y React Hook Form no sabría a qué campo asociarlo. Con path: ["confirmarContrasena"], el error llega a errors.confirmarContrasena.message y se muestra exactamente debajo del campo correcto.

noValidate en el form

El <form> tiene el atributo noValidate. Esto desactiva la validación nativa del navegador (los pequeños popups de "rellena este campo" que aparecen en rojo al enviar). El motivo es que queremos que Zod sea la única fuente de verdad sobre los errores — los mensajes del navegador tienen un estilo diferente al del diseño y no se pueden personalizar fácilmente.

7. React Hook Form: cómo se controla el formulario

El hook useForm

useForm devuelve varias utilidades que se usan en distintas partes del formulario. Las tres que usamos son:

UtilidadQué haceDónde se usa
register("campo") Devuelve props (name, ref, onChange, onBlur) para conectar un input al formulario. Se esparce con ...register() sobre el Input. En cada <Input>
handleSubmit(fn) Envuelve la función de envío: previene el reload, valida con Zod y solo llama a fn si todo es válido. En onSubmit del form
formState.errors Objeto con los errores actuales de validación. Cada clave corresponde a un campo. Si el campo es válido, no existe en el objeto. Debajo de cada Input para mostrar el error

¿Cuándo se valida?

Por defecto, React Hook Form valida al intentar enviar el formulario (mode: "onSubmit"). Después del primer intento fallido, cambia a validar también al cambiar el campo (mode: "onChange") para que el usuario vea en tiempo real si ya ha corregido el error. Este comportamiento es el mejor para formularios de registro: no molesta mientras el usuario está escribiendo por primera vez, pero da feedback inmediato en correcciones.

aria-invalid: accesibilidad para lectores de pantalla

Cada Input tiene aria-invalid={!!errors.campo}. Esto convierte el booleano de "hay error" en un atributo HTML estándar que los lectores de pantalla entienden. El doble !! convierte cualquier valor (objeto de error o undefined) en un booleano limpio (true o false). El componente Input de shadcn ya tiene estilos para aria-invalid="true": borde rojo y ring rojo.

8. NextAuth: autenticación con Google

El flujo completo paso a paso

PasoQué ocurreQuién lo gestiona
1 Usuario pulsa "Registrarse con Google" BotonGoogle → llama a signIn("google")
2 NextAuth redirige al usuario a accounts.google.com NextAuth + configuración en lib/auth.ts
3 Google muestra la pantalla de selección de cuenta Google (fuera del control de la app)
4 Usuario selecciona cuenta y acepta los permisos Google
5 Google redirige a /api/auth/callback/google?code=... Route handler [...nextauth]/route.ts
6 NextAuth intercambia el código por el token de Google y obtiene el perfil del usuario NextAuth internamente
7 NextAuth crea la sesión JWT firmada y la guarda en una cookie segura NextAuth + NEXTAUTH_SECRET de .env.local
8 El usuario es redirigido a callbackUrl (actualmente "/") NextAuth

Variables de entorno necesarias

VariableDónde se obtieneQué hace
NEXTAUTH_URL Se define manualmente en .env.local URL base de la app — NextAuth la necesita para construir las URLs de callback
NEXTAUTH_SECRET Generado con openssl rand -base64 32 Clave privada para firmar y verificar los tokens JWT de sesión
GOOGLE_CLIENT_ID Google Cloud Console → Credenciales Identifica la aplicación ante Google en el flujo OAuth
GOOGLE_CLIENT_SECRET Google Cloud Console → Credenciales Secreto para que solo nuestra app pueda intercambiar códigos por tokens
Nunca subas .env.local al repositorio El archivo .env.local está en .gitignore precisamente para que estas credenciales no sean públicas. Si NEXTAUTH_SECRET se expone, cualquiera podría forjar tokens de sesión válidos y suplantar la identidad de cualquier usuario. Si GOOGLE_CLIENT_SECRET se expone, cualquiera podría hacer peticiones OAuth en nombre de la aplicación.

¿Cómo leer la sesión en otros componentes?

Una vez el usuario está autenticado, en los componentes de la app (Fases 2-5) se puede acceder a los datos de sesión de dos formas: 

// En un Client Component:
import { useSession } from "next-auth/react";
const { data: sesion, status } = useSession();
// status puede ser "loading" | "authenticated" | "unauthenticated"
// sesion.user tiene: name, email, image (los datos de Google)

// En un Server Component:
import { getServerSession } from "next-auth";
import { opcionesAuth } from "@/lib/auth";
const sesion = await getServerSession(opcionesAuth);
if (!sesion) redirect("/login"); ← proteger rutas

9. Las animaciones en el formulario

Las animaciones en el formulario de registro son más simples que las de la landing (no hay carrusel ni whileInView), pero siguen el mismo sistema de variantes de Framer Motion. El objetivo es que la página aparezca de forma suave al cargarse y que los campos del formulario aparezcan escalonados (uno ligeramente después del otro).

Las tres variantes definidas

NombreQué animaCómo entra
variantesContenedor La tarjeta completa (motion.div raíz) opacity: 0 → 1 + y: 24px → 0 en 450 ms (easeOut)
variantesForm El <form> — solo coordina el stagger de sus hijos No anima por sí mismo — staggerChildren: 0.07 + delayChildren: 0.1
variantesCampo Cada campo individual (Label + Input + error) opacity: 0 → 1 + y: 10px → 0 en 300 ms (easeOut) 
const variantesContenedor = {
  oculto:  { opacity: 0, y: 24 },
  visible: { opacity: 1, y: 0, transition: { duration: 0.45, ease: "easeOut" } },
};

const variantesForm = {
  oculto:  {},
  visible: { transition: { staggerChildren: 0.07, delayChildren: 0.1 } },
  // staggerChildren: 0.07 → cada campo aparece 70 ms después del anterior
  // delayChildren: 0.1  → espera 100 ms antes de empezar el stagger
};

const variantesCampo = {
  oculto:  { opacity: 0, y: 10 },
  visible: { opacity: 1, y: 0, transition: { duration: 0.3 } },
};

¿Por qué el form es un motion.form?

El <form> está convertido en <motion.form> para que pueda ser el componente padre que coordina el stagger de los campos hijos. Si fuera un <form> normal, los motion.div de los campos no podrían recibir las variantes del padre automáticamente — habría que pasarlas manualmente como prop variants a cada uno.

La animación de la pantalla de éxito

Cuando el formulario se envía correctamente, la vista completa cambia. Para que este cambio no sea brusco, la pantalla de éxito aparece con una animación de escala: scale: 0.96 → 1 combinada con opacity: 0 → 1. Da la sensación de que la tarjeta "crece suavemente" hacia su tamaño final, lo que es más elegante que simplemente aparecer de golpe.
